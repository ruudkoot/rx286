# Roadmap: rx286 as a multitasking microkernel in the manner of L4

**This roadmap turns rx286 into a multitasking system built the way L4 and
seL4 are, but on the 80286's segments instead of pages.** Four layers:

- **the kernel (ring 0)** keeps only the timer, the interrupt controllers,
  the scheduler, synchronous IPC and capabilities. It allocates nothing:
  every object it keeps lives in memory the root has given it;
- **the device drivers (ring 1, IOPL 1)** are threads in address spaces of
  their own. They reach their ports directly and get their interrupts as
  notifications;
- **the root (ring 2)** starts with all the memory, the interrupt lines and
  the boot modules. It builds every other address space;
- **untrusted programs (ring 3)** reach the system through an OS server, a
  msdos.sys of sorts, which holds the driver capabilities.

The demonstration is today's shell, run as a client of the OS server, with
background programs beside it.

The plan has thirteen milestones (L1-L13). They change the kernel in place,
one step at a time, so the attack suite, the fuzzer and the storage and
device suites stay green throughout:
- **The kernel's new core (L1-L5):**
  - the program moves into an LDT, and the way back to ring 3 stops
    trusting segment registers;
  - threads and a scheduler;
  - capabilities and kernel memory;
  - IPC;
  - a root task built from boot modules.
- **An OS server takes over today's system calls (L6),** and the drivers
  then leave the kernel behind it, a few at a time (L7-L10).
- **The demonstration (L11),** then revocation (L12), then the documents
  and the release (L13).

**Writing it found:**
- **IOPL is a thread's, not a ring's.** It lives in FLAGS. A ring-3
  thread with IOPL 3 can do everything a ring-1 thread with IOPL 1 can: IN,
  OUT, CLI, LOCK (E1). "Drivers in ring 1 reach the ports" holds only
  because the kernel hands IOPL 1 to ring-1 threads and to no others.
- **Segmentation keeps a driver's pointers out of the kernel, but not its
  OUTs.** A driver can execute CLI and spin, and the timer is gone (E1: no
  tick in the whole spin). The 286 has no I/O bitmap. Any driver can also:
  - aim the DMA controller at the kernel;
  - reset the CPU, or turn A20 off, through the 8042;
  - reprogram the timer or the interrupt controllers.
- **A loaded segment register outlives its descriptor.** DS keeps working
  after its descriptor is removed or the LDT is switched, until it is
  reloaded (E3). Every return to a thread therefore reloads all four
  segment registers. Those reloads fault in ring 0 when a descriptor has
  gone, which today's kernel would treat as a panic. MAME's real 286 gives
  #SS where Bochs gives #NP.
- **`VERR` and `VERW` say yes to a segment that is not present** (E2). A
  pointer check built on them, as today's `check_buffer` is, must also test
  the present bit once revoked descriptors exist.
- **The LDT can be the capability table.** A slot whose descriptor is
  all zeros (not present, DPL 0, an invalid system type) is invisible from
  ring 3: `LAR`, `LSL`, `VERR` and `VERW` all fail, and loading it is
  #GP. The CPU never touches the slot's other seven bytes (E2).
- **No emulator here can time protected mode.**
  - **MAME's 286** runs register instructions at the right clocks. It
    charges 19 clocks for an `INT` and an `IRET` across rings, against
    Intel's 133, and its `LLDT` costs nothing.
  - **Bochs** only counts instructions (E4).

  IPC costs are therefore estimated:
  - **The bare switch,** from Intel's tables: about 314 clocks each way, or
    125 µs a round trip on a 6 MHz AT.
  - **A real call and its reply:** with the capability checks, the queues
    and the segment checks, E9's prototype ran 394 instructions (E10), some
    0.5 ms. That figure is for code written to be clear, not fast.
- **A check of the way back must fit each register's use, not only its
  presence** (E10). A slot refilled with the wrong kind of segment slips
  through a check of presence alone:
  - **Execute-only code under DS:** the kernel's own `POP DS` faulted in
    ring 0 and the prototype panicked, on all three emulators.
  - **Read-only data under SS:** the `IRET` faulted, on Bochs and MAME.

  The way back has to check each register for what that register needs
  (X3).
- **A TSS per thread costs no less on paper than switching in software**
  (E4), and in practice:
  - DOSBox-X cannot `JMP` to a 286 TSS at all;
  - Bochs and MAME disagree about the state a faulting task switch leaves
    (E5).
- **A masked interrupt line keeps one request** (E6). An interrupt that
  comes while its driver is busy is not lost: it arrives when the driver
  acknowledges. Several such interrupts arrive as one.
- **A 287 error travels with the 287's state.** On Bochs, lazy switching
  kept a pending error with its own thread (E7). On a real AT the error
  can arrive after a switch (Intel 11.4). The AT also latches BUSY until
  port F0h is written, so a careless `FRSTOR` hangs the machine.
- **The core of the design works today** on Bochs and MAME's 286. DOSBox-X
  ran the same prototype too, but no interrupt arrived there before the end.
  A throwaway prototype of 2.3 KB of kernel code (E9) has:
  - a root in ring 2 that builds three address spaces and four threads
    from untyped memory;
  - a driver thread in ring 1 that programs the real-time clock and gets
    its interrupts as notifications;
  - a client in ring 3 that calls a server in ring 1 with a badged
    capability, and passes it a segment that the server writes into;
  - seven forged, wrong or foreign capabilities, all refused.

## The request

The owner's draft, as written. It was the whole of `roadmaps/l4.md`, which
this roadmap replaces:

> - this is a draft roadmap to turn rx286 into a multitaking os
> - rx286 will be inspired by L4 / seL4 microkernels but tightly integrated with the 80286
>   - key change here is of course that the 80286 uses a segmented rather than paged memory model.
> - architecture i am looking for:
>   - the kernel (ring 0), device drivers (ring 1), and root process (ring 2) form the trusted computing base. together they make a secure system for untrusted userland (ring 3).
>   - the kernel is a state machine that manages pit, pic, thread scheduling. it does not do dynamic memory allocation. it would be handed memory to use for e.g. thread control blocks by the root process.
>   - the device drivers are fairly close to ordinary processes but as iopl = 1 and they run at ring 1 they are able to access io ports and clear the interrupt flag. this means the are inside the trusted computing base. but segmentation makes it harder for them to corrupt the kernel if they have a bug.
>   - the root process is responsible for managing memory allocation in the system and will hand it to the kernel to create threads and adress spaces. it also hold the irq capabilities it can give to the device drivers when it starts them.
> - system model
>   - the kernel does not have a true "process" entity in the unix sense. rather there are address spaces (a collection of segments) and threads running in and address space and capabilities
>   - the primary kernel syscalls are for doing ipc. we have a synchronous ipc model. a thread can wait for a message which puts it to sleep until a message is received. 
>   - messages cannot be send to arbitrary threads - there is no global namespace. to send a message you must have a capability first. capabilities (e.g. thread ids and segments) can be transfered via ipc.
>   - device drivers can also wait on interrups via ipc and an irq capability
> - as a demo the root process should start a userland program similar to the shell we have now and a couple background processes
>   - it is not sound for each userland process to access the device drivers directly so there should be msdos.sys / vfs like process that provides the typical operating system services in a safe way. this process is in a certain sense also part of the trusted computing base (though proving os-level security rather than kernel-level security). e.g. one could imagine having the root process spawning two such os processes and handing each a disjoint set of device driver capabilities.

## What the draft leaves open, contradicts, or makes dangerous

### Wrong, or true only in part

- **W1. "as iopl = 1 and they run at ring 1 they are able to access io
  ports".** IOPL is a field of FLAGS, so each thread has its own, and only
  ring 0 or a task switch can change it (Intel 10.1).
  - **What I/O needs:** CPL ≤ IOPL. Ring 1 by itself gives nothing.
  - **E1, on all three emulators:** a ring-3 thread with IOPL 3 ran IN, OUT,
    CLI and LOCK exactly as a ring-1 thread with IOPL 1 did, and a ring-2
    thread with IOPL 1 faulted on each.

  So ring 1 means I/O only if the kernel enforces it. The kernel gives IOPL
  1 to a ring-1 thread when its starter asks, and IOPL 0 to every other
  thread (E9 does this; D11).
- **W2. "segmentation makes it harder for them to corrupt the kernel if
  they have a bug".** True of a driver's pointers: a ring-1 thread cannot
  load a descriptor of DPL 0 (E1). Not true of its I/O. The 286 has no I/O
  permission bitmap, so IOPL gives "access to all I/O ports" or to none
  (Letwin, *Inside OS/2*, 18.1). Any thread with IOPL 1 can:
  - execute CLI and spin: in E1 the timer delivered no tick for the whole
    spin, and the AT has no watchdog;
  - program the 8237 to write over the kernel by DMA;
  - pulse the CPU's reset line, or turn A20 off, through the 8042
    (IBM 1-40 to 1-44);
  - reprogram the 8254, including channel 1, which refreshes the DRAM;
  - mask or acknowledge any interrupt line at the 8259As;
  - mask NMI through port 70h.

  The drivers are inside the trusted computing base for their I/O, as the
  draft says. Segments protect the kernel from their stray writes, not
  from their stray OUTs.
- **W3. "capabilities (e.g. thread ids and segments)".** A thread is a poor
  thing to send to:
  - a client holding a server thread's identity is tied to that one thread;
  - the server can only tell its clients apart if the kernel tells it who
    sent, which is a global namespace again.

  seL4 replaced L4's thread identities with *endpoints*, which any number of
  threads may wait on, and *badges* that the holder of a capability cannot
  change (Heiser and Elphinstone 2016, 3.2). D5 recommends the same: a
  thread capability exists, but it controls the thread (start, stop,
  priority) and is not used to send.

### Ambiguous, or left open

- **A1. "multitaking".** Preemptive, by priority? The demonstration's
  background programs imply that a busy program must not stop the shell.
  D9 recommends fixed priorities with round robin on the 50 Hz tick.
- **A2. "the kernel is a state machine".** There are two readings:
  - **seL4's:** one kernel stack, and every call runs to completion or
    leaves its state in the thread's control block;
  - **looser:** a small kernel stack for each thread.

  Today's kernel waits inside drivers (`ksleep_until`), so while the drivers
  move out, threads must be able to block inside the kernel (D3).
- **A3. "handed memory to use for e.g. thread control blocks".** Several
  things are open:
  - **Which objects:** thread control blocks, address spaces (an LDT and its
    capabilities), endpoints and notifications.
  - **How the kernel reaches them:** a 286 reaches memory only through a
    descriptor of at most 64 KB.
  - **How to stop the root from writing them afterwards:** if the root
    could write an LDT, it could forge any descriptor (X11).

  D7 recommends seL4's scheme in its simplest form:
  - the root holds the kernel's memory as *untyped*;
  - it *retypes* it into objects;
  - it never holds that memory as a segment it could load.
- **A4. "address spaces (a collection of segments)".** On a 286 that is an
  LDT, and LDTs are what make one selector mean different memory in
  different spaces (E2). The GDT then holds only the kernel's descriptors.
  Also open: how many segments a space may have, and who chooses.
- **A5. "capabilities ... can be transfered via ipc".** Several things are
  open:
  - copied or moved;
  - whether the giver may later take them back (revocation; D8);
  - how a receiver says where a capability should land.

  On a 286, revocation has a cost the draft does not mention (X2, X3).
- **A6. The msdos.sys / vfs-like process.** Open:
  - its ring;
  - its interface;
  - which of today's system calls it serves;
  - how programs reach it.

  D12 and D16 recommend ring 2 and DOS's services as messages. Today's
  `sys` macros would become stubs that send them, so the shell changes
  little.
- **A7. "a couple background processes".** The draft does not say what
  they do, or how they share the screen and keyboard with the shell (D19).
- **A8. "two such os processes ... a disjoint set of device driver
  capabilities".** An illustration, but a useful test of the design. The
  console and keyboard are one device, so two OS servers would need, for
  example, one on the screen and one on COM2. *Later*.
- **A9. What becomes of what exists.** The draft does not mention:
  - today's fourteen system calls;
  - the attack suite and the fuzzer;
  - the promise that no program can crash the kernel;
  - the three emulators.

  D1 recommends changing the kernel in place, so each of these holds at
  every step.
- **A10. Where programs come from.** The kernel's image carries the shell
  today. With a root, several drivers, an OS server and several programs,
  open questions are:
  - whether they come in one boot image;
  - whether the loader loads several files;
  - whether they are read from disk later (D13).
- **A11. How much memory.** Today rx286 uses the 640 KB below A20. Several
  address spaces fit in it, but extended memory is there on most ATs (D14).
- **A12. The 287, with several threads,** and its errors, which do not
  arrive when they happen (D17, X5).
- **A13. What the kernel prints, once the console is a driver's.** It
  still needs:
  - a panic screen;
  - the log on COM2 that every test reads;
  - the test hooks (D15).

### Dangerous

- **X1. A thread with IOPL can stop the machine** (W2, E1). This cannot be
  closed on a 286, only kept to few threads: the kernel grants IOPL to
  ring-1 threads only (D11).
- **X2. Revocation does not take effect until a reload.** A segment
  register keeps its descriptor after the LDT slot is cleared and after
  `LLDT` (E3).
  - **Today's `sys_write`** holds the program's ES across its interrupt
    windows. Once descriptors can change, it would go on writing into
    memory that may have been given to someone else.
  - **The ABA case:** in E3 the kernel switched LDTs during a call, and its
    own `POP DS` then loaded the same selector from the other space. The
    thread came back reading the other space's memory.
  - **Rules:** every return to a thread reloads DS, ES, SS and CS from that
    thread's LDT. The kernel never keeps a thread's segment loaded across
    an interrupt window.
- **X3. The way back to ring 3 can fault in ring 0.**
  - **With a descriptor gone** (E3):
    - the exit's `POP ES` or `POP DS` raises #NP;
    - its `IRET` raises #NP for CS, and for SS #SS on a 286 but #NP on
      Bochs.
  - **With a slot refilled by the wrong kind of segment** (E10), a check of
    presence passes and the load still faults:
    - execute-only code under DS: #GP at the kernel's `POP DS`;
    - read-only data under SS: #GP at its `IRET`.

  Today every fault in ring 0 is a panic. A fix-up at the `IRET` cannot
  help: by then the thread's AX, CX and DX are popped. So the way back
  checks each register for its own use before it pops anything:
  - **DS and ES:** readable (`VERR`) and present, or else made null;
  - **SS:** writable data, present, with DPL equal to the thread's ring;
  - **CS:** code, present, DPL equal to the ring, and IP within its limit
    (`LSL`).

  A CS or SS that fails is the thread's fault, reported as one (D18).
- **X4. `VERR` and `VERW` accept a segment that is not present** (E2).
  Today's buffer check (*docs/syscalls.md*) would pass it, and the copy
  would then fault in ring 0. The check must also test the present bit,
  which `LAR` gives.
- **X5. The 287's errors.** On a real 287 an error is signalled when the
  faulting instruction ends, which may be after the kernel has switched
  threads (Intel 11.4). Two things follow:
  - **Who is charged:** IRQ13 belongs to the thread that owns the 287's
    state, not to the one running. Today `fpu_irq` restarts "the program".
  - **The BUSY latch:** the AT keeps BUSY latched until port F0h is written
    (IBM 2-4), and `FRSTOR` waits for BUSY. An #NM handler that restores
    while the latch is set hangs with interrupts off.

  None of the emulators shows either: MAME has no 287, DOSBox-X ignores TS
  and raises no IRQ13, and Bochs reports the error at the next waiting
  instruction (E7).
- **X6. Hardware task switches fault in the new task, half loaded.** A
  `JMP` to a TSS whose DS is not present raises #NP at the new task's first
  instruction. Bochs had loaded DS's selector without its descriptor, and
  MAME's 286 had kept the old one (Intel 9.6.5; E5). With an LDT that is not present:
  - Bochs raises #TS in the new task;
  - MAME's 286 raises it at the old task's instruction, with TR already the
    new task's.

  DOSBox-X stops itself at any `JMP` to a 286 TSS. D2 recommends switching
  in software, with one TSS.
- **X7. A masked line keeps one request, not a count** (E6). Two rules
  follow:
  - **Drivers:** a driver reads its device's status, never counts its
    interrupts.
  - **The timer:** the kernel never keeps IRQ0 masked for a tick. A tick
    lost is a tick lost.
- **X8. An idle kernel must not idle on a thread's stack.** If the kernel
  waits with `sti; hlt` while a blocked thread's frame is its stack, an
  interrupt pushes a ring-0 frame without SS:SP. A later switch that
  treated that frame as the thread's would `IRET` into the kernel. The
  kernel idles on a stack of its own, or in an idle thread of priority 0
  (*The architecture*).
- **X9. Nothing here measures IPC** (E4). MAME counts ordinary
  instructions right but gives protected mode almost free. Bochs runs
  4 million instructions a second whatever they are. Every figure for the
  cost of a call is an estimate from Intel's appendix B until a real AT
  runs the timing tests (*Left open for the owner*).
- **X10. A20 is the 8042's.** IBM's BIOS leaves A20 off and Bochs leaves it
  on (E8). With extended memory in use, the keyboard driver, which drives
  the 8042 with IOPL, could turn A20 off. Every address above 1 MB would
  then wrap onto the first megabyte (D14).
- **X11. Donated memory must leave the giver's reach.** LDTs and control
  blocks live in memory the root gives the kernel. If the root could still
  load a segment over that memory, it could write any descriptor into any
  LDT. That would be every segment of the machine, at any DPL, including 0.
  In E9 the kernel's memory reaches the root only as untyped: the root can
  retype it, but never load it.
- **X12. A slot must not hint at what it holds.** A not-present data
  descriptor of DPL 3 shows its access byte to `LAR` and passes `VERR`
  (E2). A capability that is not a segment is therefore a descriptor of
  all zeros, which ring 3 cannot see.
- **X13. A server that waits for one client stops all of them** (E10). A
  receiver has one reply link, and the threads of a server are few. So a
  single-threaded OS server that calls the keyboard driver for the shell's
  key would leave the clock's call queued until the shell's key comes. Two
  remedies, both in *The architecture*:
  - one OS server thread per program;
  - a reply that can be saved into a slot and answered later.

  A driver must never *call* the OS server: Ctrl+Break and Ctrl+Alt+Del go
  as notifications. Otherwise the two can wait on each other for ever.
- **X14. Retyped memory must start empty.** If retype did not zero what it
  makes, a program would read the data of whoever had the memory before
  (from L12), and a recycled space's LDT would start with live descriptors.
  If retype could make code segments, the root could write code as data and
  run it in ring 1 with IOPL. So retype zeroes, and makes only data
  segments. Code comes only from the boot modules (D7).
- **X15. Today's calls are not reentrant.** With threads (L2), two of them
  could be inside `INT 30h` at once: two `read_key`s, or a disk call that
  waits while another starts. Until each call has moved out, the old calls
  run one thread at a time, behind one lock (L2). Today's `sys_disk_read`
  also holds the program's ES across its wait, which L1 must change (X2).

### Where this roadmap recommends otherwise than the draft

- **Endpoints, not thread identities, are what a thread sends to** (W3,
  D5).
- **The OS server is the only path to the drivers for ring 3,** as the
  draft says. It also takes over today's system calls, so the shell needs
  little change (D16).
- **No copying in the kernel beyond a few registers.** Data moves through
  segments that are passed as capabilities, not through long IPC (D5).
- **Changing the kernel in place** rather than writing a new one (D1).

## What L4 and seL4 do, and what the 286 changes

L4 is Jochen Liedtke's second-generation microkernel, and seL4 its formally
verified descendant. The draft asks for their model. Their ideas, and where
the 286 changes them:

| Idea | In L4 / seL4 | On the 286 |
|---|---|---|
| **Minimality** | a concept is in the kernel only if moving it out would make the system's functionality impossible (Liedtke 1995, 2) | the same. Liedtke "assume[s] that the hardware implements page-based virtual memory" (2); this roadmap does not |
| **Address spaces** | page tables; L4 maps, grants and flushes pages recursively | LDTs: a space is a set of descriptors; a switch is an `LLDT` (E2) |
| **Threads** | a kernel object, with registers, a priority and a space | the same; its registers live in its control block, where the CPU's frame lands (E9) |
| **IPC** | synchronous, unbuffered; call and reply-and-wait; short messages in registers; direct switch to the receiver (Liedtke 1993) | the same, with four or five words in registers: the 286 has AX, BX, CX, DX, SI, DI, BP |
| **Long messages** | L4 copied strings between spaces; seL4 dropped it as "violat[ing] the minimality principle" (Heiser and Elphinstone 2016, 4) | none: a segment is passed as a capability, and the data moves through it |
| **Names** | L4: global thread identities. seL4: capabilities in a per-thread capability space, endpoints, badges | capabilities in the LDT: a capability's name is its selector (E2, E9) |
| **Kernel memory** | seL4 allocates nothing; the root task retypes *untyped* memory into objects | the same, from an arena only the kernel maps (D7) |
| **Revocation** | L4: flush. seL4: a derivation tree, then revoke | the same tree; and every segment register reloaded before it takes effect (X2) |
| **Interrupts** | L4: messages from interrupt pseudo-threads. seL4: *notifications*, with an IRQ handler capability and an acknowledgement | notifications, since the 286 cannot interrupt into an outer ring through an interrupt gate (Intel, *iAPX 286 Operating Systems Writer's Guide*, 6) |
| **Timeouts** | L4 had send and receive timeouts; seL4 dropped them: "only the values zero and infinity were used" (Heiser and Elphinstone 2016, 4.4) | dropped too; the kernel signals a notification after a number of ticks (D6) |
| **I/O ports** | seL4 on x86: port capabilities, and kernel calls to use them | IOPL: all ports or none (W2); port capabilities only for drivers outside the trusted base (*Later*) |
| **The kernel's stacks** | L4: one per thread. seL4: one for the kernel, which is event-driven | one small stack per thread inside its control block, while threads may still block inside the kernel (D3) |

### Who did this on a 286 before

- **Minix 1.5 and 2.0** ran their device tasks in ring 1 with IOPL 1
  (`INIT_TASK_PSW 0x1200`, "with IOPL 1") and users in ring 3, with an LDT
  per process. Their message passing was a rendezvous (send, receive,
  sendrec). The tasks' descriptors covered the whole kernel image, so they
  had privilege separation without memory separation; Minix 3 moved the
  drivers out into processes of their own. (Minix sources; Tanenbaum,
  "Lessons Learned from 30 Years of MINIX", 2016.)
- **OS/2 1.x** gave each program an LDT, ran its kernel and drivers in ring
  0, and used ring 2 for "IOPL segments": code allowed I/O but not system
  calls. Ring 1 was unused (Letwin, *Inside OS/2*, 18.1).
- **iRMX II** named its objects (jobs, tasks, segments, mailboxes) by
  *tokens*, which were selectors.
- **QNX 2** ran its Send/Receive/Reply microkernel in the 286's protected
  mode.
- **Intel's own guide** recommends putting I/O code at a privilege level
  between the kernel's and the applications', with IOPL covering it. When
  "an alias is passed as part of a message", the operating system "installs
  the alias in a descriptor-table slot determined by the receiving task".
  An alias database frees a segment only when "the last descriptor for the
  segment has been deleted" (*iAPX 286 Operating Systems Writer's Guide*,
  1983, 5 and 8). That is this roadmap's segment capability, and its
  derivation tree, 40 years early.

None of them was an L4. No one is known to have built one on a 286.

## What the 80286 asks of this design

These facts shape everything that follows. They come from Intel's manual
(*References*), and the experiments checked the ones the emulators show. The
first roadmap's list (*roadmaps/rx286.md*) still holds; these are the ones
this design adds.

- **Privilege:**
  - **Rings 1 and 2 add little once every space has its own LDT.**
    - The privileged instructions (`LGDT`, `LIDT`, `LLDT`, `LTR`, `LMSW`,
      `CLTS`, `HLT`) work in ring 0 only, whatever IOPL is (Intel 10.3; E1:
      `HLT` faults in rings 1, 2 and 3).
    - A ring can load a descriptor of its own DPL or a higher one, so ring 1
      could load ring 2's and ring 3's segments, but only those in its own
      LDT or in the GDT (E1).
    - With the GDT holding only DPL-0 descriptors, a thread's ring decides
      only two things: whether IOPL 1 lets it do I/O, and which of its own
      segments it may load.
  - **IOPL is in FLAGS** (W1). `POPF` outside ring 0 never changes IOPL, and
    changes IF only at CPL ≤ IOPL, silently ignoring it otherwise (E1).
  - **`LOCK` at CPL > IOPL** is #GP on a 286 and runs on Bochs and DOSBox-X
    (E1).
- **LDTs:**
  - **Where LDT descriptors live:** an LDT's descriptor lives in the GDT,
    and `LLDT` takes its selector (Intel 10.2). An LDT holds up to 8,192
    descriptors.
  - **Slot 0 is real:** selector 04h names it. Only the GDT's slot 0 is the
    null selector (E2).
  - **What an LDT can hold:** call gates, but not LDT or TSS descriptors
    that work (E2).
  - **One selector, many spaces:** the same selector means different memory
    under different LDTs (E2).
- **Segment registers cache their descriptors.** `LLDT` does not reload
  them, and clearing a descriptor does not reach a register that holds it
  (Intel 6.6.1, 10.2: "Reload the DS and ES registers"; E3). See X2 and X3.
- **What ring 3 learns about a selector:**
  - `LAR`, `LSL`, `VERR` and `VERW` report on any descriptor the caller's
    privilege allows, present or not (E2, X4).
  - A system descriptor of DPL 0 is invisible to all four (E2, X12).
  - `SLDT` and `STR` work in ring 3 and give selectors only.
- **Interrupt handlers live in ring 0.** An interrupt or trap gate leads to
  code of the interrupted ring's privilege or greater (Intel 9.4). An
  interrupt can arrive while the kernel runs, so its handler must be ring
  0 code. Only a task gate could run a handler elsewhere, by switching
  tasks (*Operating Systems Writer's Guide*, 6). So the kernel takes every
  IRQ and passes it on (D10).
- **One frame from every ring.** An interrupt or `INT` from ring 1, 2 or 3
  pushes SS, SP, FLAGS, CS and IP on the stack of SS0:SP0 (E1). A software
  switch therefore needs only one TSS, whose SP0 points at the running
  thread's control block (E9).
- **What things cost** (Intel, appendix B, in clocks; the AT runs at 6 MHz
  with one wait state):

  | Instruction | Clocks |
  |---|---|
  | `INT n` to an inner ring, through an interrupt gate | 78 |
  | `INT n` through a task gate | 167 |
  | `IRET` to an outer ring | 55 |
  | `IRET` to another task (NT set) | 169 |
  | `CALL` through a call gate to an inner ring | 82 |
  | `RET` far to an outer ring | 55 |
  | `JMP` to a task gate | 180 |
  | `MOV`, `POP` into a segment register | 17, 20 |
  | `LLDT` | 17 |
  | `LAR`, `LSL`, `VERR`, `VERW` | 14 |
  | `ARPL` | 10 |
  | `PUSHA`, `POPA` | 17, 19 |
  | `LMSW`, `CLTS` | 3, 2 |
  | `REP MOVSW` | 5 + 4 a word |

  **The bare switch** from one space to another and back, as E4 timed it,
  is therefore some 630 clocks: about 750 with the AT's wait states, or 125
  µs at 6 MHz. Liedtke's L4 did a whole call on a 50 MHz 486 in 5 µs
  (Liedtke 1993).

  **A real call** also looks up capabilities, moves queues and checks
  segments. E9's prototype took 394 instructions for a call and its reply,
  nearly seven times the bare switch's 58 (E10). A careful fast path would
  sit between the two.
- **No instruction returns a segment's base.** A driver that programs the
  8237 needs the physical address of its buffer. The kernel or the root
  must tell it (D11). The 8237 also needs a buffer that does not cross a 64
  KB boundary.
- **The 287:**
  - **Switching it lazily:** `LMSW` can set TS (it cannot clear PE). With TS
    set, the next `ESC` instruction raises #NM (vector 7). The handler runs
    `CLTS`, `FNSAVE`s the owner's 94 bytes and `FRSTOR`s the current
    thread's (Intel 11.4; E7).
  - **A hardware task switch** sets TS by itself.
  - **Errors:** see X5.
- **A20** is off as IBM's BIOS leaves it and on as Bochs's leaves it (E8).
  Extended memory needs it on, through the 8042.
- **No `BSF`.** Finding the highest ready priority takes a table or a
  loop, not one instruction: the 386 added `BSF`.

## The experiments

Each ran on 2026-11-04 in a scratch directory, never in the repository.
- **The harness:** a small kernel (`xk`) loaded by rx286's own boot sector
  and loader, with the experiment's code included.
- **The emulators:** Bochs, MAME's IBM PC/AT (a real 286 core, IBM's BIOS)
  and DOSBox-X's 286, through the repository's own runner functions
  (`tools/rxlib.py`). Each prints on COM2 and ends with a line the runner
  waits for.
- **Their status:** none of the code is part of rx286. E9's prototype is
  the model for L2-L6, but it will be rewritten, not copied.

| | Question | Answer |
|---|---|---|
| E1 | Is I/O a ring's or a thread's? What can ring 1 with IOPL 1 do? | A thread's: IOPL is in FLAGS. Ring 1 with IOPL 1 can stop the timer |
| E2 | Can an LDT be an address space and a capability table? | Yes; a slot of all zeros is invisible to ring 3. `VERR` passes a segment that is not present |
| E3 | What do segment registers keep, and how can the way back fault? | Their descriptors, until reloaded; the exit's `POP` and `IRET` fault in ring 0 |
| E4 | What do switches and calls cost? | No emulator can tell: MAME gives protected mode free. Intel's tables: about 314 clocks each way |
| E5 | Are hardware task switches usable? | Barely: faults half-loaded, emulators disagree, DOSBox-X cannot |
| E6 | Does a masked line lose interrupts? | It keeps one request: no event lost, counts lost |
| E7 | Can threads share the 287 lazily? | Yes on Bochs; the error stays with its thread. DOSBox-X ignores TS |
| E8 | Memory above 1 MB; a bigger boot image? | Both work: A20 through the 8042, a 128 KB image with one loader change |
| E9 | Does the design work end to end? | Yes, on Bochs and MAME: 2.3 KB of kernel code. DOSBox-X ran it with no interrupt |
| E10 | What does an independent check of this roadmap find? | 17 problems, fixed here; the way back still panicked on a refilled slot |

### E1. Rings and IOPL

Small pieces of code were run, through `IRET`, in each of four settings:
- ring 1 with IOPL 1;
- ring 2 with IOPL 1;
- ring 3 with IOPL 0;
- ring 3 with IOPL 3.

The three emulators agreed except on `LOCK`:
- **The I/O instructions:** `IN`, `OUT`, `CLI`, `STI`, and a `POPF` that
  changes IF, work exactly where CPL ≤ IOPL. Ring 3 with IOPL 3 matched
  ring 1 with IOPL 1 line for line.
- **`POPF` and IOPL:** outside ring 0 it never changed IOPL. Where
  CPL > IOPL it left IF alone without a fault.
- **`HLT`:** #GP in rings 1, 2 and 3, whatever IOPL.
- **`LOCK XCHG` at CPL > IOPL:** #GP on MAME's 286; it runs on Bochs and
  DOSBox-X.
- **Loading segments:** ring 1 loaded DPL-1 and DPL-2 data from the GDT;
  DPL 0 gave #GP(0010). Ring 2 loaded DPL 2 only.
- **`INT 21h`,** whose gate has DPL 0, from any ring: #GP(010A).
- **The frames:** `INT 30h` from every ring pushed the same five words on
  SS0:SP0, and so did IRQ0 arriving in rings 1, 2 and 3.
- **Starving the timer:** a ring-1 thread with IOPL 1 that ran `CLI` and
  then a loop got no timer tick during the loop. MAME counted 0 ticks with
  IF off, against 13 for the same loop with IF on. In rings 2 and 3, `CLI`
  faulted.

### E2. An address space per LDT, and capabilities in it

Two LDTs in the kernel's data, each with a GDT descriptor, and ring-3 code
that read memory, probed selectors with `LAR`, `LSL`, `VERR` and `VERW`, and
loaded them. Identical on the three emulators:
- **One selector, two spaces:** selector 07h read 50000h under one LDT and
  60000h under the other.
- **Slot 0:** a real slot; selector 04h reads it.
- **A slot of all zeros but the kernel's own bytes** (not present, DPL 0,
  system type 0):
  - invisible to ring 3: `LAR` and `LSL` failed, `VERR` and `VERW` said no;
  - loading it gave #GP(000C);
  - the CPU never wrote the slot's other seven bytes.
- **A not-present data segment of DPL 3:** `LAR` succeeded (7300h: the
  present bit visible as 0), `LSL` gave its limit, and `VERR` and `VERW`
  said yes. Loading it gave #NP(0014).
- **A present segment of DPL 0 in the LDT:** invisible; loading it gave
  #GP(001C).
- **Other descriptors in an LDT:** a call gate of DPL 3 worked. An LDT
  descriptor was visible to `LAR` and `LSL` but unusable.
- **The edges:** a selector past the LDT's limit gave #GP(0084).
  `SLDT` and `STR` gave 0030h and 0018h in ring 3.

### E3. Descriptor caches, and the way back

A ring-3 thread whose CS, SS, DS and ES all came from one LDT, and kernel
paths that changed that LDT under it. All three emulators:
- **DS across `LLDT`:** it kept reading the old space's memory after
  `LLDT`. After `PUSH DS; POP DS` it read the new space's.
- **DS across a removal:** it kept working after its descriptor was
  cleared. A reload gave #NP(0004).
- **The kernel's exit path, after the kernel cleared a descriptor the
  thread was using:**
  - **DS or ES:** #NP(0004) at the kernel's `POP ES`, in ring 0;
  - **CS:** #NP(0034) at its `IRET`;
  - **SS:** at its `IRET`, #SS(002C) on MAME's 286 but #NP(002C) on Bochs
    and DOSBox-X.
- **`IRET` to ring 3 with DS holding a DPL-0 selector:** DS became 0, with
  no fault.
- **The ABA case:** the kernel ran `LLDT` for another space during a call.
  Its own `POP DS` then loaded the same selector from the other LDT, and
  the thread came back reading the other space's memory.

### E4. What it costs

Timed with the 8254's channel 0 (1.19 MHz) in loops of 100, interrupts
off. In ring 0, single instructions; in ring 3, with IOPL 3 so the loops
could read the timer themselves, calls and switches.

MAME's 286 runs at 6 MHz and gets register instructions right: 1,000
`NOP`s took 3,000 clocks, and `PUSHA` + `POPA` 36 (Intel: 17 + 19). Memory
operands cost more than Intel's table: `MOV AX,[BX]` took 12 clocks (Intel:
5), and `REP MOVSW` 5.6 a word (Intel: 4). For protected mode it charges
almost nothing:

| Measured on MAME | MAME | Intel, appendix B |
|---|---|---|
| `LLDT` | ~0 clocks | 17 |
| `MOV DS` | ~2 | 17 |
| `INT` + `IRET`, ring 3 → 0 → 3 | 19 | 133 |
| call gate to ring 2, `RETF` | 28 | 137 |
| software switch, A → B → A, two LDTs | 613 | about 630 (estimate below) |
| hardware switch (`JMP TSS`), A → B → A | 103 | about 630 |

Bochs runs a fixed 4 million instructions a second, whatever they are.
Neither emulator can measure IPC, so this roadmap estimates from Intel's
tables (X9).

The switch timed was the one *The architecture* recommends. It ran one
direction of a call:
- the CPU's frame lands in the thread's control block, through SP0;
- `PUSHA`, `PUSH DS`, `PUSH ES`;
- five words copied to the other thread;
- SP0 changed and `LLDT`;
- the other thread's registers popped, then `IRET`.

By appendix B that is 78 + 17 + 6 + 2 + 17 + 2 + 5 + 40 + 9 + 3 + 19 + 2 +
40 + 19 + 55 = 314 clocks. A round trip is about 630, or about 760 with one
wait state on each memory access: 125 µs at 6 MHz, 95 µs at 8 MHz.

A hardware switch is `INT` 78 + `JMP TSS` about 180 + `IRET` 55: much the
same.

Two smaller results:
- **Setting TS** with `SMSW`, `OR`, `LMSW` on each switch, for the 287,
  added 6 clocks per round trip on MAME.
- **Rewriting one GDT slot per switch** instead of keeping a descriptor per
  LDT cost 9 more instructions a switch on Bochs. On MAME it cost 140 more
  clocks a round trip, with its slow memory operands. Either way it costs
  more than a descriptor per LDT.

### E5. Task switches that fault, and DOSBox-X

The kernel's task `JMP`ed to a ring-3 task whose DS was not present, and
from there to a task whose LDT descriptor was not present:
- **DS not present:**
  - **Bochs and MAME's 286:** #NP(0014) in the new task, at its first
    instruction, with TR the new task's and its TSS busy.
  - **The new DS:** Bochs showed its selector loaded; MAME the old value.
- **LDT not present:**
  - **Bochs:** #TS(0038) in the new task, with LDTR already the new value.
  - **MAME's 286:** #TS(0038) at the old task's `JMP`, with TR the new
    task's and LDTR still the old one.
- **DOSBox-X** stopped at the first `JMP` to a 286 TSS: "E_Exit: JMP Illegal
  descriptor type 1".

### E6. Masked lines

On all three emulators:
- **IRQ0:** masked for three timer periods, then unmasked for 0.8 ms. Once
  unmasked it delivered exactly one interrupt.
- **The RTC's interrupt, IRQ8 at 1,024 Hz:** left pending for 110 ms with
  register C unread. On unmask it delivered two interrupts: the one kept,
  then the next period's after the handler read register C.
- **A handler that never reads register C:** one interrupt, then none.
  The RTC holds its line high, and the 8259A waits for an edge.

### E7. The 287 shared by threads

One ring-3 script played two threads, A and B. The kernel set TS at each
change of thread; #NM ran `CLTS`, `FNSAVE`d the owner's state and
`FRSTOR`d the new thread's.

**On Bochs:**
- A divided by zero, unmasked, just before the switch.
- B's first instruction raised #NM. The kernel saved A's state, error and
  all, and B ran on a clean 287.
- Back in A, its first waiting instruction raised IRQ13 while A ran and
  owned the 287.

**Elsewhere:** DOSBox-X raised no #NM with TS set, and no IRQ13. MAME has no
287.

### E8. Memory above 1 MB, and a bigger boot image

**Memory above 1 MB.** Writes at 0 and at 100000h, then A20 set through
the 8042 (command D0h to read the output port, D1h to write it with bit 1
set):

| | At hand-over | After setting A20 |
|---|---|---|
| Bochs, `megs: 2` | on (output port 03h) | memory answers up to 200000h |
| MAME's IBM BIOS, 1664 KB | off (EDh: 100000h wraps to 0) | memory answers up to 200000h |
| DOSBox-X | off | on, but `memsize = 1`: no memory there |

MAME's IBM BIOS needs the CMOS to declare the extended memory.

**A 128 KB `KERNEL.BIN`.** Each 512-byte sector of the padding held its own
number. The loader had three changes: it accepts a size whose high word is
nonzero, counts sectors from 32 bits, and looks for the end mark at the new
end. The image arrived whole on all three emulators. One sector at a time
through INT 13h works above 64 KB.

### E9. The core, end to end

A throwaway kernel of 2,338 bytes of 286 code: about 370 of them start the
root, and the rest are IPC, capabilities, kernel memory, scheduling and
interrupts. It runs five threads in four address spaces.

**The kernel's memory** is a 64 KB arena at 30000h that only the kernel
maps. The root holds it as an untyped capability and retypes it into:
- thread control blocks of 256 bytes;
- address spaces of 512 bytes: an LDT of 16 slots, a shadow entry per
  slot, and a GDT descriptor taken from a pool;
- endpoints and notifications of 16 bytes.

**Capabilities.** A capability is named by its selector:
- a segment capability is a real descriptor;
- any other capability is an all-zero descriptor plus its shadow entry.

**The switch.** There is one TSS. SP0 points at the end of the running
thread's control block, and the 128 bytes below the frame are that
thread's kernel stack. The way back to a thread:
- `LLDT` for its space;
- DS and ES checked with `ARPL` and `LAR`, a stale one becoming null;
- its registers popped, then `IRET`.

**IPC:**
- *call*, *receive* and *reply-and-receive*;
- a label and four words in registers, and a badge from the sender's
  capability;
- one segment capability passed per message, into a slot the receiver
  names;
- a direct switch to a waiting receiver.

**Interrupts and scheduling:**
- the RTC's IRQ8 is bound to a notification: the kernel masks the line,
  sends EOI, wakes the driver and preempts if the driver is more urgent;
- the driver acknowledges through the kernel, which unmasks the line;
- four priorities, round robin on the timer.

**The threads:**
- **The root (ring 2):**
  - made an endpoint, a notification, three spaces and four threads from
    untyped;
  - gave each space its code from the boot image, a data segment and its
    capabilities;
  - bound IRQ8 to the notification;
  - was refused a retype into a full slot (`E_ARG`) and a copy from an
    empty one (`E_CAP`).
- **A driver space (ring 1)** with two threads:
  - one with IOPL 1 programmed the RTC for 16 interrupts a second and
    counted the notifications;
  - one without IOPL served calls on the endpoint.
- **A client (ring 3)** called the server three times. Each answer carried
  the driver's count, rising (9, 18, 26 on MAME), and the badge C11Eh the
  root had minted.
  - **A passed segment:** the client passed its buffer with a call. It
    arrived in the server's chosen slot as 002Dh, the server wrote
    "HELLO" through it, and the client read `HE` back from its own buffer.
  - **Refused with `E_CAP`, all seven:**
    - a GDT selector (the kernel's data);
    - a segment used as an endpoint;
    - an empty slot;
    - a selector past the LDT;
    - an endpoint passed as a segment;
    - a retype from an endpoint;
    - the root's selector for its untyped, which in the client's LDT names
      the client's endpoint.
  - **Its DS** was intact at the end.
- **A spinner (ring 3, priority 0)** ran whenever nothing else could. It
  had asked for IOPL 3 and got 0.

**On MAME's 286:** 62 switches, 26 interrupts, 9 calls. Bochs behaved the
same, with fewer interrupts in the time. DOSBox-X (`cycles = max`) ran the
whole test before its first timer tick or RTC interrupt. There it checked
IPC and capabilities, but not preemption or notifications.

**Not tried:**
- revocation;
- the kernel's timer;
- faults sent to a handler;
- the 287;
- queues of several senders;
- priority inheritance.

### E10. An independent check

A fresh reader, given this roadmap's draft, the experiments, Intel's
manual and the repository, reviewed the draft and re-ran E9 with changes.

**The review found 17 problems.** Each is fixed in this roadmap:
- **The way back was not safe** (X3).
- **Several gaps in the design:**
  - a passed capability dropped when the receiver's slot was full,
    with no way to empty it before L12 (D5, L4);
  - one reply link per server thread (X13);
  - retype that did not zero (X14);
  - today's calls not reentrant (X15);
  - the direct switch's rule about priorities (D9);
  - the frame of a fault with an error code (D18);
  - 287 errors that would fault a restarted thread again (D17).
- **Overstatements:**
  - the cost of IPC;
  - MAME's clocks;
  - what DOSBox-X tested;
  - the room for the kernel's code during the move (*Constraints*).
- **Slips:** in the call table, the counts and the citations.

**The changed prototype.** E9 with:
- 32 slots a space;
- faults in rings 1-3 sent to a fault endpoint;
- CS and SS checked like DS and ES, for presence only, as the draft said;
- a call that moves a capability out of another space, standing in for
  revocation;
- priorities set per thread, and a check for a thread resumed while a
  better one was ready.

Bochs, MAME and DOSBox-X, three runs each:
- **The cost of a call:** a call and its reply between a ring-3 client and
  a ring-1 server took 394 instructions on Bochs, against 58 for E4's bare
  switch. On MAME it took 2,961 clocks, which still leaves out most of the
  protected-mode costs.
- **A segment moved out of a space while its thread held it in DS:** the
  way back nulled DS on all three. The thread's next read was its own
  #GP(0000) in ring 3, reported to the root, with no panic. DOSBox-X read
  through the null DS without a fault, as *docs/emulators.md* already
  records.
- **Three senders on one endpoint:** they queued to depths 1 and 2 and were
  served first come, first served, each with its own badge. The third
  sender's segment never arrived: the server's receive slot was still full
  from an earlier call, and its call succeeded anyway.
- **A ring-1 thread with IOPL 1 that ran `CLI`, then `HLT`:** #GP(0000) in
  ring 1, reported as that thread's fault. The timer ticked on afterwards.
- **A call to a server of lower priority than the caller:** with the
  draft's rule (switch only to a receiver at least as urgent), the caller
  waited 5 ticks for a thread of middle priority on all three. With E9's
  rule (always switch), the server ran while a better thread was ready.
- **A slot refilled with another kind of segment while the thread held its
  selector:**
  - execute-only code under DS: the kernel panicked at its own `POP DS` on
    all three;
  - read-only data under SS: the kernel panicked at its `IRET` on Bochs
    and MAME, and DOSBox-X stopped itself;
  - a slot just emptied: caught as the thread's fault on all three.

## Constraints

- **The machine is still the AT of `roadmaps/rx286.md`:** an 80286 and an
  80287 at 6 MHz, 640 KB, an EGA, two diskette drives, two fixed disks, two
  serial and two parallel ports. There is no BIOS after the loader and no
  hardware detection.
- **Only 286 instructions.** `check-286` runs over every binary, the
  modules' included.
- **Every milestone leaves `make check` green** on Bochs, DOSBox-X and MAME,
  and changes the documents it touches.
- **The kernel allocates nothing** (the draft). Every object it keeps after
  start lives in memory the root retyped.
- **No global namespace** (the draft). A thread can name only what its
  capabilities name. The GDT holds only the kernel's descriptors (DPL 0).
- **No program can crash the kernel,** as today (*docs/security.md*). The
  promise grows to "no program can reach what it holds no capability for"
  (*The security model*).
- **Small.** The goal is a kernel's code under today's 8 KB room once the
  drivers have left (L10). During the move both worlds are in the kernel:
  - today 2.8 KB of the room is free;
  - E9's core is 2.3 KB, and E10's 3 KB, without the timer, the 287 or
    minting.

  So L3 grows the room to 16 KB, and L10 measures what is left.

## The architecture

As the recommendations of *Decisions* would make it. Where a decision
could change a part, the part names it.

### The rings, and the trusted computing base

| Ring | Who | IOPL | What it may do |
|---|---|---|---|
| 0 | the kernel | | everything; in it: IPC, capabilities, threads, the scheduler, the timer, the interrupt controllers, the 287, NMI, the panic screen, the log |
| 1 | the drivers | 1 | their devices' ports, `CLI`; their own segments |
| 2 | the root; the OS server | 0 | their own segments; the root holds all memory and every interrupt line, the OS server every driver's endpoint |
| 3 | programs | 0 | their own segments, and what their capabilities name |

**What a ring is.** A space's ring is the DPL of its slot 0, its code
segment. The ring is fixed when the root fills that slot, and the space's
threads run at it.

**What the kernel enforces of the rings** is one thing: IOPL 1 goes only
to a ring-1 thread (D11). A segment may be passed to a space of any ring.
A ring-1 driver can load a ring-3 program's buffer, as in E9, and a ring-3
program cannot load a ring-1 segment, so passing one gives it nothing.

Everything else is capabilities. Ring 2 is a label the root and the OS
server wear (D12).

### Kernel objects

| Object | Size | What it holds |
|---|---|---|
| thread (TCB) | 512 B | its kernel stack (E9's paths need 128 B; L2 measures today's waiting calls); the frame its entry saves (32 B); state, priority, links; its space; its reply link; its fault endpoint; its bound notification; 94 B for the 287 |
| address space | 16 B a slot | an LDT of 16 to 256 slots (8 B each) and a shadow entry per slot (8 B: type, rights, object, badge); a GDT descriptor from the pool |
| endpoint | 16 B | a queue of waiting senders or of waiting receivers |
| notification | 16 B | a word of bits, and the thread waiting on it |
| untyped | (none) | a range of memory, and how much of it has been retyped |
| segment | (none) | a real descriptor in an LDT slot |
| IRQ handler | (none) | an interrupt line |

**Where they live.** Every object of the first four kinds lives in the
*arena*: 64 KB that only the kernel maps, through one GDT descriptor (D7).
An object is aligned to its size, so no object crosses 64 KB.

**Capacity.** The arena holds, for instance, 32 spaces of 64 slots (32 KB),
48 threads (24 KB) and 512 endpoints and notifications (8 KB).

### Capabilities

**A capability's name is its selector:** slot n of the caller's LDT is n ×
8 + 4 + its ring. The kernel reads a selector from a register; anything
other than an LDT selector within the LDT's limit is refused (`E_CAP`).

**A segment capability *is* its descriptor.** The program loads it into DS
or ES and the CPU checks every access. Its rights are the descriptor's own:
writable or not, its limit.

**Any other capability is a descriptor of all zeros,** invisible to the
program (E2), and its shadow entry says what it is:

| Type | Rights | Calls |
|---|---|---|
| untyped | | retype |
| segment | (the descriptor's) | pass in a message; ask its physical base (for DMA). Data only from retype; code only over the boot modules |
| space | | copy, move, mint into it; configure a thread into it |
| thread | | configure, start, suspend, priority |
| endpoint | send, receive, grant; a badge | call, send, receive, reply-and-receive |
| notification | signal, wait; a badge | signal, wait, poll; bind to an interrupt or a thread |
| IRQ handler | | bind to a notification; acknowledge |
| reply | (one use) | reply: kept in the receiver's TCB, never in a slot |

**Copy, move and mint.** These put a capability into a slot of a space the
caller holds:
- *copy* duplicates it;
- *move* empties the source;
- *mint* copies with fewer rights or a badge, and a badged capability
  cannot be badged again.

Every copy and mint records its parent for L12's revocation (D8).

### The kernel's memory, and memory for everyone else

At start the kernel gives the root:
- the arena, as untyped;
- the free memory, as untyped in pieces of up to 64 KB;
- a segment over each boot module (*The boot*).

**Retype** makes an object at the untyped's next aligned address, and
zeroes it (X14):
- **Kernel objects** come only from the arena's untyped.
- **Segments** come from any untyped other than the arena's, at a size and
  DPL the root chooses. They are data segments only.
- **Code segments** exist only over the boot modules the kernel found. They
  are given to the root at start. The root decides which module runs in
  which ring, but cannot run code of its own making.

Nothing is ever mapped twice by accident: an untyped's memory is either
retyped or not, and a retyped piece is not given out again until L12's
revoke empties it.

The physical map, with the recommendations of D13 and D14:

| Range | What |
|---|---|
| 00000h-0FFFFh | the BIOS's tables and the loader, as today; never used after the start |
| 10000h-3FFFFh | `KERNEL.BIN`: the kernel, then the boot modules (up to 192 KB) |
| 40000h-4FFFFh | the arena |
| 50000h-9FFFFh | untyped: the root's to retype (320 KB) |
| A0000h-FFFFFh | the EGA, the ROMs |

### The GDT and the IDT

The GDT is fixed, all DPL 0:
- the kernel's code, data and stack;
- the TSS and the double-fault task's TSS and stack;
- the screen, for the panic writer;
- the arena;
- a pool of LDT descriptors, one per space, which retype takes from and
  revoke gives back.

Programs see nothing of the GDT (E1, E2).

The IDT is today's, plus:
- **vector 31h,** the kernel's calls, an interrupt gate of DPL 3;
- **vector 30h,** today's calls, until L10 deletes them (D20).

### The switch

There is one TSS (D2). Its SP0 points at the end of the running thread's
frame in its control block. The CPU's five words and the entry's `PUSHA`,
`PUSH DS` and `PUSH ES` land in the control block, and the 128 bytes below
are the thread's kernel stack (D3).

**The way back to a thread** (E9):
- SP0 is set to the thread's control block;
- `LLDT` for its space;
- each segment register is checked for its own use, after `ARPL` against
  the thread's ring (X3):
  - **DS and ES:** present (`LAR`'s bit, since `VERR` ignores it) and
    readable (`VERR`), or else made 0;
  - **SS:** present, writable data, DPL equal to the ring;
  - **CS:** present, code, DPL equal to the ring, IP within its limit;
- a CS or SS that fails means the thread has faulted, and its fault
  handler hears of it instead (D18). E9 checked presence only, and E10 made
  it panic;
- the frame is popped, and `IRET`.

**Idling.** When no thread is ready, the kernel idles on its own stack with
`sti; hlt`. An interrupt that arrives there is taken on that stack and ends
by choosing a thread (X8).

### The kernel's calls

`INT 31h`. AH is the call, and AL a label or flags. DX names the capability
acted on, and BX, CX, SI and DI are four words of message. BP names a
capability to pass, or the slot that is to receive one. A call returns its
status in AL, with CF set on an error. Call 12 returns data in AL, so its
status is CF alone.

| AH | Call | In | Out |
|---|---|---|---|
| 1 | call | DX endpoint; AL label; BX CX SI DI; BP a capability to pass | AL status; BX CX SI DI the reply; BP the capability received |
| 2 | reply and receive | BX CX SI DI the reply; DX endpoint; BP receive slot | AL label; DX badge; BX CX SI DI; BP the capability received |
| 3 | receive | DX endpoint or notification; BP receive slot | as 2; for a notification BX its bits |
| 4 | send | as call | AL status: never waits for a reply |
| 5 | signal | DX notification | |
| 6 | poll | DX endpoint or notification | as receive, or `E_EMPTY` at once |
| 7 | retype | DX untyped; AL type; SI destination slot; CX size and BL access byte (a segment), or CX slots (a space) | |
| 8 | copy, move, mint | DX space; SI source slot; DI destination slot; AL copy, move or mint; BX badge or rights | |
| 9 | thread | DX thread; AL configure (SI space, BX IP, CX SP, DI fault endpoint), start (CL priority, CH 1 to ask for IOPL), suspend, resume, or priority (CL). Configure only a suspended thread; suspend takes a thread off every queue and clears its reply links | |
| 10 | interrupt | DX IRQ handler; AL bind (SI notification) or acknowledge | |
| 11 | timer | DX notification; CX ticks: the notification is signalled once, that many ticks on | |
| 12 | segment | DX segment: its physical base (DL:AX) and limit (CX) | |
| 13 | delete | DX one of the caller's own slots: emptied (from L4) | |
| 14 | save reply | SI an empty slot: the reply link moves there, to be answered later with send (from L4) | |
| 15 | revoke | DX slot: every capability derived from it deleted (L12) | |
| 0, 16 | in debug and test builds: print, end the test | | |

The capability calls are seL4's, cut to what a 286 and this system need.

### IPC

- **Rendezvous:** synchronous and unbuffered. An endpoint holds a queue of
  senders or of receivers, never both.
- **Call:**
  - **When a receiver waits:** the message goes straight to it: the label,
    four words, the badge of the sender's capability, and one capability
    if the endpoint capability has the grant right. The caller then waits
    for its reply.
  - **When none waits:** the caller queues.
- **The reply:** a one-time link kept in the receiver's control block, as
  in seL4's first design. A server that cannot answer at once saves it into
  a slot (call 14) and answers through it later, as the OS server does for
  a key (X13). A reply goes only to a caller still waiting on that link. A
  caller that is suspended or deleted loses its link, and a reply to it
  fails. E9's prototype checked neither, and a stale reply could have
  answered a later call.
- **Reply and receive:** answers the last caller and waits for the next in
  one call, as L4's ReplyWait does.
- **A capability passed:** it lands in the slot the receiver named, if that
  slot is empty. If it is not, the message arrives without it, and the
  receiver sees BP = 0 (seL4's rule). Servers delete what they received when
  they have done with it (call 13); E10's server, unable to, could receive
  one segment ever.
- **Direct switch:** the kernel switches straight to the receiver when the
  receiver's priority is at least the sender's (Liedtke 1993's direct
  switch, with seL4's rule about priorities). Otherwise the receiver is
  made ready and the scheduler chooses. A reply to a caller of higher
  priority than the replier switches to it at once, and so does a start or
  a wake-up of a thread above the running one.
- **Servers above their clients:** under the rule above, a server below its
  client makes the client wait for every thread between them. E10 measured
  5 ticks. The root therefore runs each server at or above the priority of
  every client it gives the server's endpoint to (*Scheduling*).
- **Data larger than four words** goes through a segment the two share.
  Typically the client passes one with the call, or the root gave both
  sides a capability to it at start (D5). The kernel never copies more
  than registers.
- **Notifications:**
  - *signal* ORs the signaller's badge into the notification's word;
  - *receive* on a notification returns the word and clears it, or waits;
  - a thread can have a *bound* notification, so a receive on an endpoint
    also returns when the notification is signalled. A driver can then
    serve calls and its interrupt in one loop.
- **Timeouts:** there are none (D6). A driver that must give up on its
  device arms the kernel's timer, which signals its notification after a
  number of ticks.

### Scheduling

Eight fixed priorities, round robin within each, a time slice of a few
50 Hz ticks, and a table that maps an 8-bit mask of the non-empty queues to
the highest priority, since the 286 has no `BSF` (D9).

The root sets each thread's priority. By its policy:

| Who | Priority |
|---|---|
| interrupt threads | 7 |
| the root | 6 |
| drivers | 5 |
| the OS server | 4 |
| programs | 1-3 |

Every server sits above its clients (*IPC*).

### Interrupts

The kernel keeps three lines, which no handler capability names:
- **IRQ0,** the timer: the ticks, time slices, the kernel's timer;
- **IRQ2,** the cascade: never masked;
- **IRQ13,** the 287's error: charged to the thread that owns the 287
  (X5).

**IRQ7 and IRQ15** keep today's check for spurious interrupts before they
are signalled.

**Every other line** may be bound by its IRQ handler capability to a
notification (D10):
- the kernel masks the line, sends EOI and signals the notification;
- the driver services its device and acknowledges, which unmasks the line;
- an interrupt that came in the meantime is kept by the 8259A (E6).

A line nobody has bound keeps today's rule: reported once, then masked.

### Faults

A thread that faults is suspended. The kernel sends its fault handler
endpoint a message: the vector, the error code, CS:IP and the thread's
badge. An exception with an error code pushes one word more, so the kernel
moves the frame up by that word first. The control block's layout is then
the same for every way in. The handler replies to restart the thread at an IP, or does not
reply and leaves it suspended (D18).

**Who handles whose faults:**
- the root handles the drivers' and the OS server's;
- the OS server handles its programs'. It reports a fault and restarts the
  program, as the kernel does today.

A fault in the kernel is a panic, as today.

### The 287

**Lazy switching** (D17, E7):
- TS is set at every switch to another thread;
- #NM saves the owner's state into the owner's control block and restores
  the new thread's;
- the owner is remembered.

**Errors.** IRQ13 writes port F0h at once, then charges the error to the
owner (X5), through its fault handler. Today's `fpu_irq` clears the error
with `FNCLEX`. The kernel does the same to the owner's saved state, so a
thread restarted by its handler does not meet the error again.

### The boot

**The image.** `KERNEL.BIN` is the kernel, a module table, then the
modules:
- the root;
- the drivers;
- the OS server;
- the shell and the background programs.

Each module is built as today's program is: its code and data at fixed
offsets of its own binary. The loader's one change is a size of more than
64 KB (E8; D13).

**The kernel's start** does what `start.asm` does today, then:
- builds the arena, the root's space and the root's thread;
- gives the root its capabilities:
  - its own code and data;
  - the arena and the free memory, as untyped;
  - every IRQ handler but the kernel's own four;
  - a read-only segment over each module, and a segment describing them
    (name, size, offsets);
- runs the root.

**The root:**
- builds the drivers' spaces, each with its code (a code segment over its
  module), a data segment initialised from the module, a stack, its IRQ
  handlers and its timer notification;
- starts their threads, with IOPL 1 for those that touch devices;
- builds the OS server, with an endpoint to each driver;
- builds each program, with an endpoint to the OS server badged with the
  program's number, and a transfer segment it shares with the OS server;
- waits, to handle the faults of what it started.

### The drivers

**Their shape.** Each driver is a ring-1 space with a thread that has
IOPL 1, one bound notification for its interrupt and its timer, and one
endpoint it serves. Its protocol is small:
- a block device reads or writes a sector through a segment the caller
  passes;
- a character device writes or reads bytes through one;
- the keyboard gives keys, and the console writes, clears and moves the
  cursor.

**Today's limits carry over:** one sector a call, 4,096 bytes a write.

**The diskette driver** gets a DMA buffer from the root: a 512-byte
segment, which cannot cross 64 KB because it is aligned. It asks the
kernel for its physical base (call 12).

**The drivers keep today's code.** The device code moves largely as it is.
What changes is how it waits: on its notification instead of
`ksleep_until`, and on the kernel's timer instead of `kpoll`'s count of
ticks.

### The OS server

A ring-2 space that holds an endpoint to every driver. It serves programs
in DOS's way (D16):
- **today's calls as messages:** write, read a key, ticks, time, print,
  sound, joystick, mouse, serial, wait;
- **the disks:** sectors, and files once the FAT12 code moves in from the
  shell (L9).

**How a program calls it.** Each program has a 4 KB transfer segment it
shares with the OS server. A call names an offset and a length in it. The
`sys` macro of `syscalls.inc` becomes a stub with the same registers, so
the shell's code changes little:
- **Buffers:** the stub checks the program's buffer as `check_buffer` does
  today, and returns `E_FAULT` before it copies. So today's attack lines
  hold.
- **Long results:** results longer than a reply's four words, such as
  `SYS_JOYSTICK`'s, come back in the transfer segment.

**One thread per program.** The OS server serves each program's endpoint
with a thread of its own. A program waiting for a key or a sector then
holds up no other (X13).

**The screen and keyboard** are the OS server's:
- the program in the foreground has the screen and the keys;
- a background program may write only to a status line (D19).

**Ctrl+Break and Ctrl+Alt+Del** are signalled by the keyboard driver on
notifications, never sent as calls (X13):
- **Ctrl+Break:** the OS server restarts the foreground program.
- **Ctrl+Alt+Del:** the keyboard driver, which drives the 8042, resets the
  machine itself, as today's kernel does. The root has no port to do it
  with.

### The demonstration

The shell, as today, in the foreground, beside two background programs:
- a clock, which keeps the time in the top line's corner;
- a counter at the lowest priority, which shows on the status line that it
  runs only when nothing else does.

New shell commands:
- `ps` lists the threads (the root keeps the list; the kernel has none);
- `kill` and `start` act on a background program through the root (D19).

### The builds

Release, debug and test, as today:
- **Debug and test builds** print the kernel's lines on COM2, each with
  the thread's name, and offer the kernel's print call to every thread.
- **Test builds** also offer the end-of-test call, and the hooks the tests
  use to type keys and provoke devices. Their keys reach the keyboard
  driver as the 8042 delivers them, through command D2h on Bochs; on MAME
  through the driver's own test entry, where IBM's 8042 has no D2h.

## The security model

### The promise

Today's promise is that no program can crash the kernel
(*docs/security.md*). It extends to every ring, each to its degree:

| Who | Can never | Trusted for |
|---|---|---|
| a program (ring 3) | read or write memory it holds no segment for; name an object it holds no capability for; touch a port; disable interrupts; make the kernel fault, panic, reset or hang; keep a capability after it is revoked (from L12) | nothing |
| the OS server (ring 2) | the same, except that it holds the drivers' endpoints | what programs may do with devices and files: the OS-level security of the draft |
| the root (ring 2) | touch a port, or the kernel's memory | memory, and which thread gets which capability |
| a driver (ring 1, IOPL 1) | load a kernel descriptor, or any segment it was not given | its device, and everything its I/O can reach: the whole machine (W2, X1) |
| the kernel | | everything |

A program that spins is preempted: it can keep the CPU only from threads
whose priority is not above its own, and the root chooses the priorities.

### What holds it

- **Descriptors:**
  - **The GDT holds only DPL-0 descriptors,** and nothing outside ring 0 can
    load them (E1).
  - **Every LDT and control block lives in the arena,** which no thread can
    load (X11).
  - **An LDT changes only through the kernel's calls,** each of which checks
    the caller's capabilities.
- **Capabilities:**
  - **A selector names a slot of the caller's own LDT,** or is refused. A
    GDT selector, a slot past the limit, an empty slot or a slot of
    another type gets `E_CAP` (E9).
  - **A capability that is not a segment is invisible** (E2, X12).
- **I/O:** IOPL 1 is given only to ring-1 threads (D11), and the kernel's
  own lines (timer, cascade, 287) cannot be bound to a notification.
- **The way back** checks each of the four segment registers for its own
  use before it pops anything. A revoked, moved or refilled segment is then
  the thread's fault, never the kernel's (X3).
  The kernel holds no thread's segment across an interrupt window (X2).
- **Buffers.** The OS server and the drivers check a passed segment
  themselves. The kernel copies only registers, so no buffer of a program
  is ever read in ring 0.
- **The 287's errors** go to the 287's owner (X5).
- **What stays as today:** the double-fault task, the check of the return
  IP, the rule for every vector, the IDT's limit and the gates of DPL 0.

### What is outside it

- **A driver's I/O** (W2). A ring-1 driver is trusted with the machine; a
  bug there can stop it.
- **The root's policy.** It can give any memory to anyone.
- **Denial of service by priority.** A program the root runs at a high
  priority can starve those below it. The root decides the priorities.
- **Hardware faults,** a double fault inside the double-fault task, and
  physical access, as today.

### The attacks

Today's 59 attacks stay, run from ring 3. New ones, each with its exact
expected line:
- **From ring 3, at capabilities** (E9's seven, and more):
  - every kernel call with a GDT selector, an empty slot, a slot past the
    LDT, each wrong type;
  - a badge changed by minting twice;
  - passing a capability without the grant right;
  - retyping into a full slot, beyond an untyped's end, or into the
    arena's untyped for a segment;
  - a reply to someone else's call.
- **From ring 3, at the LDT:**
  - loading every slot of every type;
  - `LAR`, `LSL`, `VERR` and `VERW` on each, which must see only segments;
  - a moved segment still in DS (X2);
  - a slot refilled under a loaded selector with another kind of segment:
    execute-only code under DS, read-only data under SS, data under CS
    (E10).
- **From ring 2:** `IN`, `OUT`, `CLI`; loading the arena or the kernel's
  data; starting a thread with IOPL; binding the timer's line.
- **From ring 1:** `HLT`, `LGDT` and the other privileged instructions;
  loading the arena or the kernel's data.
- **Against the scheduler:**
  - a ring-3 spinner at the program priority, which the shell must
    survive;
  - a thread that suspends itself while holding a reply;
  - a call to an endpoint nobody receives on, which must be breakable with
    Ctrl+Break.

### The fuzzer

Today's fuzzer stays: random code in ring 3. It gains:
- random calls to `INT 31h` with random selectors and random words;
- random messages to the OS server.

The kernel's checksum of its code and tables, at every restart, extends to
the arena's invariants: every LDT descriptor in the pool still points at a
space, and every queue is well formed.

## Debugging

- **Bochs' debugger:** `info ldt` shows the running space's LDT. The
  kernel's map gives the arena's layout, and `make debugger` loads symbols
  for every module at its base.
- **A thread dump,** in debug builds: on a panic, or on the AT's SysRq
  key, the kernel prints every thread's name, state, priority, space and
  CS:IP. Debug builds keep a list of threads for this. The kernel itself
  needs none.
- **Each module is assembled alone** with its own map, as the shell is
  today, so a fault's CS:IP turns into a symbol by module.

### D1. How the kernel gets there

**Decided: A** (2026-11-04), as recommended. The draft describes the end. Today's kernel is a working
system with 195 tests.

- **A. In place, a step at a time.** **Recommended.**
  - **How:** each milestone changes the kernel while today's system calls
    go on working, until each has a new home. Martin Fowler's "strangler"
    pattern, applied to a kernel.
  - **For it:**
    - the attack suite, the fuzzer, the storage and device suites run at
      every commit;
    - each step is small enough to review;
    - the program never stops working.
  - **Against it:**
    - the kernel serves two worlds for a while (L2-L10), and some code is
      written to be deleted (L10);
    - today's calls were written for one program and are not reentrant, so
      from L2 they run one thread at a time, behind one lock (X15);
    - the kernel's code needs a room of 16 KB until L10 (*Constraints*).
- **B. A new kernel beside the old one** (`src/l4/`), swapped in when it
  reaches today's features.
  - **For it:** a clean start.
  - **Against it:** months without the suites' help. Everything is
    rewritten twice, and the swap is one big risk.
- **C. Replace the kernel at once.** B without the safety of the old one.

### D2. The switch

**Decided: A** (2026-11-04), as recommended.

- **A. One TSS; switch in software** (E4, E9). **Recommended.**
  - **How:** SP0 points into the running thread's control block, and a
    switch is SP0, `LLDT`, the pops and `IRET`.
  - **For it:**
    - about the same clocks as a hardware switch (E4);
    - no GDT slot per thread;
    - faults during a switch are the kernel's own code's, which it can
      check first (X3);
    - DOSBox-X can run it (E5).
  - **Against it:** the kernel saves and restores the registers itself,
    and sets TS itself (`LMSW`, 3 clocks).
- **B. A TSS per thread; `JMP` to switch.**
  - **For it:** the CPU saves everything, sets TS, and loads LDTR.
  - **Against it:**
    - a GDT slot per thread;
    - faults in the new task with registers half loaded (X6);
    - Bochs and MAME disagree on the state after #TS (E5);
    - DOSBox-X cannot run it at all (E5);
    - #TS and a not-present stack then need task gates of their own
      (Intel 9.6.4).
- **C. The kernel as a task, reached through task gates.** Each kernel
  entry costs 167 clocks instead of 78, and each exit 169 instead of 55;
  B's troubles too.

### D3. The kernel's stacks

**Decided: A** (2026-11-04), as recommended. The draft calls the kernel "a state machine".

- **A. A small stack per thread, inside its control block** (E9).
  **Recommended** while the kernel still has calls that wait inside it
  (L2-L10).
  - **How:** the 128 bytes below the thread's frame. A call that waits
    leaves its stack there, and another thread runs.
  - **For it:**
    - today's `read_key`, `ksleep_until` and the disk calls keep working
      unchanged, inside the thread that made them, until they move out;
    - Intel's own example of 287 switching keeps a task's kernel stack
      beside its state (Intel 11.4).
  - **Against it:**
    - E9's paths fit in 128 bytes, but today's waiting calls were written
      with a kernel stack of 1 KB and their depth was never measured. L2
      measures it, with a watermark in debug builds, and sizes the block to
      it;
    - a check at entry, in debug builds, that SP is above the block's
      floor.
- **B. One kernel stack; every call runs to its end or leaves its state in
  the control block** (seL4).
  - **For it:**
    - the purest "state machine";
    - smaller control blocks;
    - no stack per thread to overflow.
  - **Against it:** it cannot carry today's waiting calls through the move.
    It fits only once the drivers are out (after L10).

  A can become B after L10 if wanted: by then no kernel path waits.

### D4. Where capabilities live

**Decided: A** (2026-11-04), as recommended.

- **A. In the LDT** (E2, E9). **Recommended.**
  - **How:** a slot is a capability, and its selector is its name.
    Segments are real descriptors, everything else an all-zero
    descriptor. A shadow entry of 8 bytes per slot holds type, rights,
    object and badge.
  - **For it:**
    - a segment capability is checked by the CPU on every access, for
      nothing;
    - one table to keep consistent, not two;
    - the program needs no translation from capability to selector;
    - Intel's guide already treats descriptors in messages so (*What L4
      and seL4 do*).
  - **Against it:**
    - a space has at most 8,192 capabilities;
    - a capability's name is tied to its slot;
    - a slot costs 16 bytes.
- **B. A separate capability table (seL4's CNode),** with a segment
  capability mirrored into an LDT slot when the thread wants to load it.
  - **For it:** seL4's model as it is; guarded lookups; spaces of capability
    tables.
  - **Against it:** two tables per space to keep in step, and a mapping call
    before every use of a segment.
- **C. Global thread identities (L4 X.2).** The draft rules this out: "no
  global namespace".

### D5. IPC

**Decided: A** (2026-11-04), as recommended.

- **A. Endpoints and badges; a label and four words in registers (BX, CX,
  SI, DI); at most one capability a message; nothing copied but
  registers.** **Recommended.**
  - **Data:** larger messages go through a segment the two sides share.
  - **The reply:** a one-time link in the receiver's control block.
  - **For it:**
    - E9 runs it;
    - the 286 has seven usable registers, and Liedtke found register
      messages the largest single gain (Liedtke 1993, table 1);
    - seL4 dropped long messages (Heiser and Elphinstone 2016, 4).
  - **Against it:**
    - a program that has to send bytes needs a shared segment: its
      transfer segment (D16);
    - a capability arrives only if the receiver's slot is empty, so
      receivers must delete what they received: *delete* comes with IPC,
      in L4, not with revocation (E10);
    - a server thread holds one reply link, so a server that must wait for
      something on one client's behalf saves the link into a slot (X13).
- **B. A, plus an IPC buffer per thread:** a segment of 64 words the kernel
  copies between threads (seL4's IPC buffer).
  - **For it:** longer messages without sharing memory.
  - **Against it:** the kernel needs both threads' buffers at once, which
    on a 286 means two GDT windows or the `LLDT` trick (E3). Copying is
    `REP MOVSW` at 4 clocks a word.
- **C. L4's string copies.** B, and more of it.

### D6. Timeouts

**Decided: A** (2026-11-04), as recommended. Today every wait for a device has a limit in ticks, and the
promise "no device can hang the kernel" rests on it.

- **A. No IPC timeouts; a kernel timer that signals a notification after a
  number of ticks** (call 11). **Recommended.**
  - **How:** a driver waits for its interrupt or its timer, whichever comes
    first, since both signal its bound notification.
  - **For it:** seL4's reasons for dropping timeouts (only zero and
    infinity were used; Heiser and Elphinstone 2016, 4.4). The kernel keeps
    one sorted list of armed timers.
  - **Against it:** a client calling a server that never answers waits for
    ever. Ctrl+Break, through the OS server, is the user's way out.
- **B. L4's timeouts on send and receive,** in ticks.
  - **For it:** a client can give up on a server.
  - **Against it:** every call carries a timeout; the kernel keeps a list of
    every waiting thread; seL4's experience.
- **C. Neither.** Drivers would poll, as `kpoll` does today. That keeps the
  CPU busy, and a busy driver at a high priority starves everything below
  it.

### D7. The kernel's memory

**Decided: A** (2026-11-04), as recommended. "It would be handed memory to use for e.g. thread control
blocks by the root process."

- **A. An arena: 64 KB that only the kernel maps, which the root holds as
  untyped and retypes into objects** (E9). **Recommended.**
  - **For it:**
    - one descriptor, near offsets for every object;
    - the root can never write an object (X11);
    - seL4's untyped and retype in their simplest form.
  - **Against it:** at most 64 KB of objects (*The architecture*: about 32
    spaces and 48 threads), and the size is fixed at assembly.
- **B. Windows over all memory: ten GDT descriptors of 64 KB each, so the
  root may retype any untyped into kernel objects.**
  - **For it:** no fixed limit.
  - **Against it:**
    - every object access needs a window's selector;
    - the untyped kept for kernel objects must never also be given out as
      segments, which needs the derivation records of D8 from the start.
- **C. A descriptor per object.** One GDT slot per thread and per space:
  thousands of slots, and a `MOV ES` before every access.

### D8. Revocation

**Decided: A** (2026-11-04), as recommended.

- **A. Delete from L4; revoke not until L12; every copy and mint records
  its parent from L3 on.** **Recommended.**
  - **Delete:** a thread can empty a slot of its own from L4, which
    receivers need (D5). Nothing is freed yet.
  - **How, in L12:** a recursive *revoke*, memory given back to its
    untyped, with the reloads and checks of X2 and X3.
  - **For it:**
    - the demonstration needs no revocation: programs are restarted, not
      destroyed;
    - the hard part on a 286 is not the tree but the cached registers,
      and L1 already makes the way back safe for it.
  - **Against it:** a background program's memory cannot be reused until
    L12. `kill` stops it, but its memory stays given.
- **B. The derivation tree and revoke from L3.** Complete earlier; L3
  doubles.
- **C. Never revoke: a space's capabilities go only when the space goes.**
  Simple, but then memory is never reused.

### D9. Scheduling

**Decided: A** (2026-11-04), as recommended.

- **A. Eight fixed priorities, round robin within each, a time slice of a
  few ticks.** **Recommended.**
  - **How:** a table maps the bitmap of non-empty queues to the highest
    one; the 286 has no `BSF`.
  - **For it:** the scheduler of L4 and of seL4 without its MCS extension.
    Interrupt threads come first by priority alone.
  - **Against it:**
    - a thread of high priority that spins starves those below it (*What is
      outside it*);
    - with the direct switch's rule, a client above its server waits for
      every thread between them. E10 measured 5 ticks of it. So servers run
      above their clients, which is the root's rule to keep
      (*Scheduling*).
- **B. Round robin only.** Simplest, but an interrupt waits behind every
  ready program for its turn.
- **C. Budgets (seL4's MCS).** Bounded, but it doubles the scheduler, for a
  machine with one user.

### D10. Interrupts

**Decided: A** (2026-11-04), as recommended. "device drivers can also wait on interrups via ipc and an
irq capability."

- **A. The kernel masks the line, sends EOI and signals the bound
  notification; the driver's acknowledgement unmasks it** (E6, E9).
  **Recommended.**
  - **For it:** seL4's IRQ handler. A slow driver blocks only its own line.
    The 8259A keeps a request that arrives meanwhile (E6), so none is lost.
  - **Against it:** two kernel entries per interrupt (the wake-up and the
    acknowledgement), some 300 clocks by Intel's tables.
- **B. The driver sends EOI itself, with IOPL.**
  - **For it:** one kernel entry fewer.
  - **Against it:** an interrupt of the same line can arrive before the
    driver runs. A forgotten EOI blocks every line of lower priority at the
    8259A, the timer included if it is the master's.
- **C. Task gates straight into the drivers.** The only way to run a
  handler outside ring 0 (Intel 9.4). D2 B's troubles, and DOSBox-X lost.

### D11. What drivers may do

**Decided: A** (2026-11-04), as recommended.

- **A. As the draft says.**
  - **How:** a ring-1 thread may have IOPL 1 if its starter asks, and no
    other thread may have IOPL; the drivers are trusted with the machine
    (W2). The kernel keeps the timer, the interrupt controllers and NMI by
    convention.
  - **For it:** the draft; Minix did it (*What L4 and seL4 do*); the
    devices' code moves as it is.
  - **Against it:** a driver's bug can stop the machine (X1).
  - **Recommended.**
- **B. No IOPL: port capabilities, used through kernel calls** (seL4 on x86,
  Minix 3).
  - **For it:** the kernel controls which ports each driver reaches.
  - **Against it:**
    - a port access becomes a kernel call, about 200 clocks instead of 3;
    - a fixed disk's sector is 256 words through one port;
    - the modem's bytes at 9600 baud leave 1 ms each.
- **C. A for the disks and the console, B for the slow devices** (printer,
  mouse, game port, RTC). *Later*: after L10, any driver can be moved to B
  alone.

### D12. The rings of the root and the OS server

**Decided: A** (2026-11-04), as recommended. The draft puts the root in ring 2. It does not say where the
OS server goes.

- **A. Both in ring 2, as the draft says.** **Recommended.**
  - **For it:** the draft's layering, in which each ring trusts the ring
    below it. It costs nothing (E9's root ran in ring 2).
  - **Against it:** ring 2 gives no power that ring 3 lacks once each space
    has its own LDT (*What the 80286 asks of this design*). It is a label,
    and the roadmap says so.
- **B. Both in ring 3; only the drivers in another ring.** Authority comes
  from capabilities anyway, and one fewer kind of space to test.
- **C. The OS server as a library in ring 2, reached through call gates in
  each program's LDT** (OS/2's IOPL segments, Letwin 18.1).
  - **For it:** a call gate costs 82 + 55 clocks against an IPC's 600 or so.
  - **Against it:** the OS server's data would be in every program's space.
    A program that dies in the middle of a call leaves it half changed.

### D13. How programs reach memory

**Decided: A** (2026-11-04), as recommended.

- **A. One boot image: the kernel and a table of modules, loaded by the
  loader as one file** (E8). **Recommended.**
  - **For it:**
    - one change to the loader;
    - the root starts with every module in memory, as seL4's root does
      with its boot modules;
    - the image is checked as one (`check-image`).
  - **Against it:** the image grows with every program, up to 192 KB here.
- **B. The loader loads several files.** The loader's three sectors would
  have to hold a list of names and a table, for little gain over A.
- **C. The OS server loads programs from disk, through its FAT12 code.**
  **Later:** it needs the file system in the OS server (L9) and a program
  format. It is the natural next step after L11 (*Later*).

### D14. Memory

**Decided: A** (2026-11-04), as recommended.

- **A. 640 KB, as today.** **Recommended.**
  - **For it:**
    - with A of D13 and D7 there are 320 KB of untyped for programs;
    - nothing touches A20 or the bochsrc (`megs: 1`);
    - MAME's CMOS stays as it is.
  - **Against it:** about twenty programs of today's shell's size.
- **B. Extended memory too: A20 set at start, untyped above 1 MB given to
  the root** (E8).
  - **For it:** 15 MB more on an AT with it.
  - **Against it:**
    - A20 belongs to the 8042, which the keyboard driver drives (X10);
    - the emulators' configurations and MAME's CMOS change;
    - the DMA controller reaches only the first 16 MB, and its page
      registers only 64 KB pages.

  *Later*.

### D15. What stays in ring 0

**Decided: A** (2026-11-04), as recommended. "the kernel is a state machine that manages pit, pic,
thread scheduling".

- **A. Today's kernel minus every device driver.** **Recommended.** The
  kernel keeps:
  - the timer's channel 0 and the interrupt controllers;
  - the 287's switching and IRQ13;
  - NMI;
  - a panic writer that writes the screen directly;
  - in debug and test builds, the log on COM2 that every test reads, and
    the test hooks.
- **B. A, minus the log and the panic writer.** Purer, but then a panic is
  silent, and every test would depend on a ring-1 serial driver being
  alive to say what happened.
- **C. A, plus the keyboard,** so that Ctrl+Alt+Del works even when every
  driver is dead. The keyboard is a device like any other. With a dead
  keyboard driver, Ctrl+Alt+Del is the power switch's job: the IBM AT has
  no reset button.

### D16. The OS server's interface

**Decided: A** (2026-11-04), as recommended. "msdos.sys / vfs like process that provides the typical
operating system services".

- **A. Today's system calls as messages.** **Recommended.**
  - **How:** a stub replaces each `sys` with the same registers in and
    out. Buffers go through a transfer segment of 4 KB that each program
    shares with the OS server. Files come in L9 as new calls (open, read,
    close, find), in DOS's way.
  - **For it:** the shell, the test programs and their expected transcripts
    barely change; today's buffer limits (4,096 bytes) are the transfer
    segment's size.
  - **Against it:**
    - a copy into the transfer segment for every write;
    - the stub must check the buffer itself (as `check_buffer` does) to
      keep today's `E_FAULT` answers;
    - results longer than four words come back through the transfer
      segment;
    - the OS server needs a thread per program, so that one program's wait
      holds up no other (X13).
- **B. A POSIX-like interface.** No program of rx286 wants it.
- **C. Today's `INT 30h` kept, and forwarded by the kernel to the OS
  server.** The program would not change at all. But the kernel would have
  to know the OS server and copy buffers, against the minimality the draft
  asks for.

### D17. The 287

**Decided: A** (2026-11-04), as recommended.

- **A. Lazy switching; errors to the 287's owner** (E7, X5).
  **Recommended.**
  - **How:** TS is set at every switch; #NM saves and restores 94 bytes in
    the control blocks; IRQ13 writes port F0h and goes to the owner's fault
    handler.
  - **For it:** Intel's own scheme (11.4); a thread that never uses the 287
    never pays for it.
  - **Against it:**
    - on a real AT it cannot be tested here (X5);
    - the owner's thread may already be blocked when its error comes;
    - the kernel must clear the error in the owner's saved state when it
      reports it, as today's `FNCLEX` does, or a restarted thread meets it
      again.
- **B. One thread at a time may use the 287;** EM is set for every other,
  whose `ESC` faults. Simple, but programs would have to ask for the 287.
- **C. Save and restore at every switch.** 94 bytes each way, about 200
  clocks per switch, for nothing in most switches.

### D18. Faults

**Decided: A** (2026-11-04), as recommended.

- **A. A fault suspends the thread, and the kernel sends its fault handler
  a message** (seL4's fault endpoint, L4's pager). **Recommended.**
  - **Who handles what:** the root handles drivers and the OS server; the
    OS server handles its programs. The OS server reports a fault and
    restarts the program as the kernel does today. Today's fault lines and
    the attack suite's expected lines stay.
  - **For it:** policy out of the kernel; the attack suite's 59 lines
    survive.
  - **Against it:**
    - a thread without a fault handler is suspended for ever;
    - an exception with an error code pushes one word more, which the
      kernel must take out of the frame before it can restart the thread at
      an IP.
- **B. The kernel reports and restarts, as today.** Policy in the kernel,
  and "restart" means nothing for a driver.

### D19. The demonstration

**Decided: A** (2026-11-04), as recommended. "the root process should start a userland program similar
to the shell we have now and a couple background processes".

- **A. The shell; a clock and a counter in the background; `ps`, `kill`
  and `start`.** **Recommended.**
  - **The clock** writes the time in the top line every second, through the
    OS server's status line.
  - **The counter** runs at the lowest priority and shows how much of the
    CPU is left.
  - **`ps`** asks the root for its list of threads; `kill` and `start` ask
    it to stop or start a background program.
  - **For it:** each part shows something: preemption, priorities, IPC,
    isolation, and a program that dies while the others live on.
- **B. A, plus a print spooler** that takes `print` jobs and prints while
  the shell works on.
  - **For it:** shows a server written as a program.
  - **Against it:** more for little more shown. *Later*.
- **C. Two OS servers with disjoint drivers** (the draft's example): one on
  the screen and keyboard, one on COM2 with drive B. **Later:** it needs a
  terminal on COM2 and a second set of programs.

### D20. The kernel's call vector during the move

**Decided: A** (2026-11-04), as recommended.

- **A. The kernel's new calls on `INT 31h`; today's calls on `INT 30h`
  until L10 deletes them.** **Recommended.**
  - **For it:**
    - the two never mix;
    - the attack suite's `INT 31h` line ("beyond the IDT's limit") moves
      to `INT 32h`, and that is all;
    - after L10, vector 30h faults like any other.
  - **Against it:** one more gate of DPL 3.
- **B. One vector, new numbers above today's 14.** One gate fewer. But the
  new calls and the old ones would share a dispatcher, and L10 would have to
  renumber.

## The milestones

Each milestone is one commit or a few. Each commit leaves `make check`
green and updates the documents it touches, and each milestone records
itself in *Status*. Sizes are in lines of assembly and tools, with
comments: S is up to 300, M up to 800, L more.

The order follows D1: the kernel changes in place. Today's system calls
keep working until L10, and every suite of today runs at every step.

### L1. The program in an LDT; a safe way back to ring 3 (M, about 500)

* **What:**
  - **The program's segments** (and the fuzzer's alias) move from the GDT
    into an LDT of one space, in the kernel's data. The GDT keeps only
    DPL-0 descriptors. `selectors.inc` gives the program's selectors as
    LDT selectors.
  - **The way back** (`interrupt.asm`) checks DS and ES with `ARPL`, `LAR`,
    the present bit and the segment bit, and nulls a stale one. A CS or SS
    that has gone is the program's fault, and the program restarts (X3).
  - **The buffer check** (`check_buffer`) also tests the present bit (X4).
  - **`write`, `print` and `serial_write`** re-check their buffer after each
    interrupt window, rather than trusting ES across it (X2).
    `sys_disk_read` stops holding the program's ES across the transfer: it
    loads and checks it again for the copy.
  - **Test probes** that change one of the program's descriptors during a
    call, standing in for revocation. Each probe either clears a slot or
    refills it with another kind of segment: execute-only code under DS,
    read-only data under SS, data under CS (E10).
* **Done when:**
  - `make check` is green, with the attack suite's selector lines updated;
  - new attacks:
    - each kind of LDT slot of E2, loaded and probed;
    - a selector past the LDT;
    - `LAR` and `VERR` on each;
  - with the probes, a cleared or refilled DS comes back as 0, a cleared
    or refilled CS or SS is the program's reported fault, and none is a
    panic.
* **Decisions:** D1, D4.

### L2. Threads and the scheduler (L, about 1,000)

* **What:**
  - **Thread control blocks:** two, in the kernel's data for now (the arena
    comes in L3). The software switch: SP0 into the running block, `LLDT`,
    the checked way back (D2, E9). The kernel stack inside each block
    (D3).
  - **A wait inside the kernel blocks only its thread.** `read_key`,
    `ksleep_until`, `ksleep` and `SYS_WAIT` save the kernel's SP in the
    block and switch, and the interrupt that ends the wait makes the
    thread ready again.
  - **Today's calls behind one lock** (X15). A second thread that enters
    `INT 30h` while another is inside waits at the door until it leaves.
    `kpoll`'s busy waits stay as they are until their drivers leave.
  - **The kernel stack per thread, measured:** a watermark in debug builds
    shows the deepest of today's calls, and the control block is sized to
    it (D3).
  - **The scheduler:**
    - eight priorities and the table;
    - time slices on IRQ0;
    - idling on the kernel's own stack (X8).
  - **The 287:**
    - TS set at each switch;
    - #NM saves and restores 94 bytes;
    - IRQ13 writes F0h and goes to the owner (D17, X5).
  - **A second program,** `counter`, in its own LDT, started by the kernel
    beside the shell.
* **Done when:**
  - `tests/threads` passes:
    - the shell answers keys while `counter` spins at the same priority,
      and at a lower one;
    - a spinner at a higher priority starves only those below it;
    - two threads keep their own 287 states (Bochs);
  - every suite of today is green;
  - the debug build's thread dump shows both threads.
* **Decisions:** D2, D3, D9, D17.

### L3. Capabilities and kernel memory (L, about 900)

* **What:**
  - **The arena and untyped;** retype into control blocks, spaces,
    endpoints, notifications and segments (D7).
  - **The LDT as the capability table,** with shadow entries; the pool of
    LDT descriptors in the GDT (D4).
  - **Copy, move and mint,** each recording its parent (D8).
  - **`INT 31h`** and the calls of *The architecture* that L3 needs: 7, 8, 9,
    12 (D20).
  - **Retype zeroes** what it makes, and makes data segments only (X14).
  - **The kernel builds the two programs' spaces and threads** from the
    arena, as a root will in L5.
  - **The kernel's code room grows to 16 KB** (`layout.inc`): the old calls
    and the new core live side by side until L10 (*Constraints*).
* **Done when:**
  - `tests/caps` passes: every retype, copy, move and mint, and every
    refusal, E9's seven among them;
  - host tests cover retype's alignment and the selector arithmetic;
  - the attack suite gains the capability attacks of *The security
    model*.
* **Decisions:** D4, D7, D8, D20.

### L4. IPC: endpoints, notifications, the kernel's timer (L, about 900)

* **What:**
  - **IPC:** call, send, receive, reply-and-receive, poll; badges; the
    reply link, and saving it into a slot (call 14); one capability a
    message, into an empty slot only; the direct switch and its rule about
    priorities; a reply or wake-up that switches to a more urgent thread
    (D5).
  - **Delete** (call 13): a thread empties a slot of its own, so a server
    can receive capabilities over and over (D8).
  - **Notifications,** bound and not.
  - **The kernel's timer** (call 11; D6).
  - **The fuzzer** calls `INT 31h` with random selectors and words.
  - **`tests/timing`** counts the IPC path's instructions on Bochs.
* **Done when:**
  - `tests/ipc` passes:
    - a ping and pong of 1,000 calls between two programs;
    - queues of three senders, served in order with their badges;
    - a capability passed, used, deleted, and passed again;
    - a capability passed to a full slot, arriving as BP = 0;
    - a saved reply answered later;
    - notifications signalled while their waiter was busy;
    - the timer;
    - a client above its server, and a client below it, with the times
      E10 measured improved by the rule about servers' priorities;
  - 10,000 fuzz iterations pass with no panic or changed checksum.
* **Decisions:** D5, D6, D9.

### L5. The root task and the boot image (L, about 900)

* **What:**
  - **The loader** reads a `KERNEL.BIN` of more than 64 KB (E8).
  - **The image:** a module table and modules, built by a new tool and
    checked by `check-image`.
  - **The kernel's start** gives the root its capabilities (*The boot*).
  - **The root** (`src/root/`, ring 2) builds the shell's space from its
    module and runs it.
  - **Faults go to a fault endpoint** (D18): the root handles the shell's
    for now. It prints today's fault line and restarts the shell, so the
    attack suite's expected lines stay.
* **Done when:**
  - the shell runs as before, started by the root;
  - `tests/root` passes: the modules where the table says, a fault reported
    by the root, a module missing from the image refused by the loader's
    checks;
  - every suite of today is green.
* **Decisions:** D12, D13, D18.

### L6. The OS server takes over the system calls (L, about 900)

* **What:**
  - **The OS server** (`src/os/`, ring 2) serves today's calls as messages
    (D16), with one thread per program (X13).
  - **For each call, the OS server itself makes today's `INT 30h` call**
    on its own transfer segment, so nothing moves yet but the path. The
    kernel's buffer checks hold for a ring-2 caller as for a ring-3 one.
  - **The `sys` macro becomes a stub** over the program's transfer segment,
    for the shell and the test programs. The stub checks a buffer as
    `check_buffer` does, and returns `E_FAULT` before copying. Results longer
    than four words come back in the transfer segment.
  - **The OS server handles the programs' faults** in the root's place.
* **Done when:**
  - every suite of today passes, with the shell and the test programs going
    through the OS server;
  - the attack suite's lines are unchanged, now printed by the OS server;
  - the transfer segment's limits are tested: a call past its end,
    `E_FAULT`.
* **Decisions:** D16, D18.

### L7. Interrupts as notifications; the first drivers out (M, about 700)

* **What:**
  - **IRQ handler capabilities,** bind and acknowledge (D10).
  - **The printer driver** (polled, with the kernel's timer) and **the

  - **The OS server talks to them,** not to `INT 30h`, for `print` and
    `mouse`.
  - **The kernel's `printer.asm` and `mouse.asm` are deleted.**
* **Done when:**
  - the storage suite's printer tests and the device suite's mouse tests

### L8. The console and the keyboard out (L, about 900)

* **What:**

### L9. The disks out; FAT12 in the OS server (L, about 1,100)

### L12. Revocation (M, about 700)

* **What:**
  - **Revoke,** recursive, along the parents recorded since L3.
  - **Memory goes back to its untyped** when the last capability to it goes,
    so `kill` frees a program's memory. Retype zeroes it before it is used
    again (X14).
  - **A space revoked with threads in it:**
    - its threads are suspended and taken off every queue;
    - their reply links and the reply links naming them are cleared;
    - its LDT descriptor goes back to the pool only when no thread names it
      any more.
* **Done when:**
  - `tests/revoke` passes:
    - a revoked segment still loaded in DS is gone at the next return;
    - E3's ABA case cannot recur;
    - a revoked endpoint fails its queued callers with `E_CAP`;
    - memory freed by `kill` is retyped again;
  - the fuzzer gains revoke and delete.
* **Decisions:** D8.

### Why this order

- **The way back (L1) first.** Every later step changes descriptors under
  running code. With the checks in place first, a mistake shows as a
  reported fault, not a panic in ring 0.
- **Threads (L2) before capabilities (L3).** Two programs scheduled by
  priority are useful at once, and every later test runs with them.
- **IPC (L4) after capabilities,** since it passes them.
- **The root (L5) before any driver leaves,** because the root holds the
  interrupt lines and the memory the drivers need.
- **The OS server (L6) before the drivers (L7-L10).** Programs need one
  place to call while devices move one at a time. With the OS server in
  place, each driver's move is invisible to the shell and the tests.
- **Simple drivers first (L7):** the printer and the mouse have small
  protocols and their own tests. The console and keyboard (L8) come next
  because every test reads the one and types on the other. The disks (L9)
  bring DMA and the file system.
- **The demonstration (L11)** once nothing is left in the old kernel.
- **Revocation (L12) last.** Nothing before needs it, and it changes the
  most delicate code once everything else is still.

## Risks

| Risk | What it would do | What reduces it |
|---|---|---|
| A driver's I/O stops or corrupts the machine (W2, X1) | a hang, or a write anywhere by DMA | drivers are few and in the trusted base; IOPL only for ring 1; the drivers' code is today's, tested; port capabilities *Later* |
| A segment register outlives a revoked descriptor (X2) | a thread reads memory given to another | every return reloads all four; nothing held across a window; L1's probes; L12's tests |
| The way back faults in ring 0 (X3) | a panic a program can cause | L1's checks before `IRET`; the attack suite's cleared-descriptor attacks |
| The 287's errors on a real AT differ from Bochs (X5) | an error charged to the wrong thread, or a hang at `FRSTOR` | port F0h written first; errors charged to the owner; untestable here, recorded as such |
| IPC is too slow on a 6 MHz AT (E4: 125 µs a round trip for the bare switch; E10: E9's path some 0.5 ms) | the shell feels slow; the modem's bytes overrun: the AT's 16450 holds one byte, a new one every 1.04 ms at 9600 baud | registers only, direct switch, reply-and-receive; the interrupt reaches the modem driver through one kernel entry and one switch, not a call; a fast path for call and reply once it works; the kernel turns a 16550's FIFO on where there is one, as today; a real AT measures |
| The emulators cannot measure protected-mode costs (E4) | a slow path unnoticed | `tests/timing` counts the instructions on Bochs; Intel's tables give the estimates; *Left open* asks for a real AT |
| The kernel's stack per thread is too small for one of today's calls | a write past it, into the frame | L2 measures the deepest call and sizes the block; a check of SP at entry in debug builds; the paths that wait leave with the drivers (D3) |
| A server waits for one client and stops the rest (X13) | the clock stops while the shell waits for a key | one OS server thread per program; saved replies; drivers signal, never call, the OS server |
| The kernel's code outgrows its room during the move | the build stops (by design) | the room grows to 16 KB in L3; L10 measures what is left |
| The arena fills (D7: 64 KB) | the root cannot start more | sizes in *The architecture* leave room; `make sizes` reports the arena's use at the demonstration's start |
| Bochs differs from a 286 in a way the design relies on (#SS against #NP, `LOCK`, A20, TS on DOSBox-X) | a test passes that the AT would fail | MAME runs every suite; the known differences listed in *docs/emulators.md* |
| The move takes longer than the end state alone would (D1) | effort spent on code L10 deletes | L6's OS server makes each driver's move small; the suites catch every slip |
| The draft's ring 2 means more to the owner than a label (D12) | a design that does not do what was meant | asked; the owner took D12 A, ring 2 as a label (*Left open for the owner*) |
