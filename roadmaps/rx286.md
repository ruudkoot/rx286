# Roadmap: rx286, a minimal 80286 microkernel for the IBM PC/AT

**rx286 is a microkernel and operating system for the IBM PC/AT, written in
assembly for the 80286 in protected mode.** Its first delivery is four things
on one FAT12 floppy:
- **a boot sector** that loads a boot loader;
- **a boot loader** that uses the BIOS to load `KERNEL.BIN` from the FAT file
  system;
- **a kernel** that never calls the BIOS. Its tables (GDT, IDT, TSS) are
  written out at assembly time, it handles every interrupt, and no ring-3
  program can crash it;
- **a demonstration shell** in ring 3, carried inside the kernel's image, that
  takes commands from the keyboard.

Debug, release and test builds come from one source. The roadmap also covers
the tests, a Bochs set-up that can be debugged, the documents, and
`make doctor`.

This roadmap plans the first delivery in eleven milestones:
- **Tooling first (M1):** the repo, the Makefile, `make doctor`, the Bochs
  configurations, and a test runner that boots an image headless in half a
  second and reads its serial output.
- **Boot (M2, M3):** a boot sector with stage 2 in the FAT's reserved sectors,
  and a loader that follows `KERNEL.BIN`'s cluster chain.
- **The kernel (M4-M6):**
  - protected mode with prefilled tables, and a panic path that cannot
    triple-fault;
  - drivers for the console, timer, keyboard, serial log and 287, and a rule
    for every IRQ;
  - ring 3 and five system calls whose pointers are checked by the 286's own
    instructions.
- **The shell (M7)** and **an attack suite with a fuzzer (M8),** which hold the
  kernel to the claim that no program can crash it.
- **Proof on a real 286 core (M9),** then the documents (M10) and the release
  (M11).

**Writing it found:**
- **Bochs cannot be an 80286.** Its oldest CPU is a Pentium-class
  `bx_generic`, which here reports itself as a 64-bit Athlon (E3). Code that
  uses a 386 instruction runs in Bochs and would fail on the AT. So the
  roadmap adds a check of the binaries (M1) and runs the suites on a real
  286 core (M9).
- **NASM's `cpu 286` lets 386 code through:** 32-bit addressing (`[ebx]`,
  `a32`) and `mov ax, fs` assemble without a word (E4).
- **`mformat -C` writes the mtools process's own memory into the floppy
  image,** so images are not reproducible, and they leak (E5). There is a
  recipe that is byte-for-byte reproducible.
- **NASM's `section.X.start` cannot be split into a descriptor's base bytes**
  (E4). The image therefore has a fixed layout of constants, which suits
  "everything hard coded".
- **Two traps for the kernel,** found by an independent check (E10):
  - **Bochs starts with a live LDT at address 0**, which a ring-3 program can
    load descriptors from unless the kernel loads LDTR with a null selector.
  - **Masking IRQ2,** the cascade, cuts off the 287's error interrupt, and the
    program's next 287 instruction then stalls.

**The core of the design works in Bochs today.** A 9.7 KB throwaway prototype
does the following (E6):
- enters protected mode with prefilled tables and remaps the PICs;
- takes timer and keyboard interrupts, with keys injected through the 8042
  (E7);
- runs ring 3 with a system call;
- catches 19 hostile ring-3 actions, each as the expected exception with the
  expected error code, including a 287 error arriving on IRQ13 (E8);
- rejects bad system-call pointers;
- exits Bochs on its own, all in 0.45 s.

It was written on 2026-11-03 against an empty repository: `roadmaps/rx286.md`,
the owner's draft, was its only file. The roadmap replaces that file. The
draft is kept verbatim in *The request*.

## What the draft leaves open, contradicts, or makes dangerous

### Wrong, or impossible as written

- **W1. "do ensure the bochs configuration matches with the kernel
  configuration."** It can match only in part:
  - **The CPU:** Bochs 2.7 has no 80286. Its CPU models start at
    `bx_generic` and `pentium` (`bochs --help cpu`). The CPU it runs reports
    itself as an x86-64 Athlon with an xAPIC (E3). It runs any 386 or later
    instruction that a 286 would reject.
  - **Instructions:** a `LOCK` prefix at CPL 3 runs in Bochs, where a 286
    faults. A program's `IRET` with NT set may not raise the same exception
    on both (*E10*).
  - **The start-up state:** Bochs starts with a live LDT and with A20 on
    (*E10*).
  - **The video card:** Bochs has VGA, not EGA. VGA is a superset of the EGA
    registers the kernel uses (the CRTC's cursor registers and colour text at
    B8000h).
  - **What does match:** the I/O map, the IRQs, the memory, the drives, the
    keyboard type (`keyboard: type=at`), the serial and parallel ports, and
    the 287's IRQ13 (E3, E8).

  The roadmap therefore does three things:
  - holds the code to the 286 by a check of the binaries (M1);
  - writes descriptors whose reserved top word is zero, which makes a 386 or
    later behave as a 286 (*What the 80286 asks of the design*);
  - runs every suite on a real 286 core (M9, D1).
- **W2. "all COM port on the usualy IRQs":** COM3 and COM4 share IRQ4 and
  IRQ3 with COM1 and COM2. ISA interrupts are edge-triggered, so two cards on
  one line cannot both be served reliably. IBM's AT defined COM1 and COM2
  only; COM3 and COM4 are a later convention. The kernel drives none of them
  for input (D20), so the sharing matters only to the rule for unhandled IRQs
  (D12).
- **W3. "all LPT port":** LPT1 at 378h uses IRQ7 and LPT2 at 278h uses IRQ5.
  The third conventional address, 3BCh, lives on IBM's monochrome adapter,
  which this machine lacks because it has an EGA.

### Ambiguous, or left open

- **A1. How much memory.** The draft lists the hardware but not the RAM. An AT
  had 256 KB or 512 KB on the board (IBM, 1-12), and 640 KB plus extended
  memory was common. The roadmap assumes 640 KB of base memory and uses
  nothing above it. Bochs' `megs: 1` gives 639 KB base, with 1 KB kept by
  its BIOS, and no extended memory (*E10*, D6).
- **A2. "do not do any kind of hardware detection".** Three things look like
  detection and are not:
  - the boot drive in `DL`, which the BIOS hands the boot sector;
  - the geometry in the boot sector's BPB, which is the file system's own
    record;
  - polling a controller's status register before writing to it (the 8042,
    the UART).

  None of them asks what hardware exists. The kernel reads none of them
  except the status polls.
- **A3. "the userland program can be included in the kernel":** in the same
  source, or as a separate binary inside the kernel's image? D5 recommends a
  separate binary, assembled on its own and included with `incbin` at a fixed
  offset. It can then reach the kernel only through the system calls, even
  in its source.
- **A4. "ensure all CPU interrupts and IRQs are handled ... by printing ... for
  anything unhandled (even in release builds)".** Four cases need a rule
  that printing alone does not give:
  - **A device that keeps interrupting:** this is rare without a driver,
    since most devices wait for their driver's acknowledgement. The RTC
    raised IRQ8 once and then waited for its register C to be read (*E10*).
    A faulty or misprogrammed device can still do it, and would flood the
    screen.
  - **A device that interrupts once:** a floppy controller's reset interrupt
    is never acknowledged if no driver exists.
  - **Spurious interrupts:** the 8259A delivers IRQ7 or IRQ15 when a line
    drops before the CPU acknowledges it. These must not be acknowledged with
    an EOI as if they were real.
  - **NMI:** on the AT it means a parity error or an I/O channel check.

  D12 and D13 give the rules.
- **A5. Line 27, "ensure everything", is cut off.** The roadmap reads it as
  "ensure everything is tested". Every module, system call, vector and IRQ
  line has a test (*Testing*). The owner should say whether more was meant
  (*Left open for the owner*).
- **A6. "no crashing of the system possible".** Here is what the roadmap can
  promise:
  - **Ring 3:** no ring-3 program can make the kernel fault, hang, reset, or
    read or write outside its own segments.
  - **A program that spins** cannot hang the machine: Ctrl+Break restarts it
    (D11).
  - **A kernel bug** is caught by the panic path, which prints and halts and
    never resets silently (D13).

  Nothing can survive a hardware fault (an NMI from a parity error), or a
  fault inside the double-fault handler itself. Those are reported if
  possible and otherwise reset.
- **A7. "debug build will print additional information ... release builds
  adhere to minimalism", but every unhandled event is printed "even in
  release builds".** The two fit together:
  - **Release** prints faults, unhandled IRQs and panics, and nothing else.
  - **Debug** also traces boot steps and every system call, and mirrors the
    screen to COM1.
  - **A third flavour, test,** adds what the automatic tests need (D16).
- **A8. "make doctor ... with the right versions".** No versions are given.
  The roadmap pins each tool to the version tested here, as a minimum. Bochs
  is pinned to its minor version, since its configuration syntax changes
  between releases (*Tooling*).

### Dangerous

- **X1. The BIOS leaves IRQ0-7 on vectors 8-15,** which in protected mode are
  the CPU's own exceptions: 8 is a double fault and 13 is a general
  protection fault. The kernel must reprogram both 8259As before it enables
  interrupts. Otherwise the first timer tick looks like a double fault.
- **X2. The BIOS switches the floppy motor off from its own timer
  interrupt.** Once the kernel owns IRQ0, a motor the loader left running
  stays on forever. The loader switches it off (M3).
- **X3. INT 13h fails a read that crosses a 64 KB physical boundary,**
  because of the 8237's DMA. The loader reads one sector at a time into a
  64 KB-aligned image (M3).
- **X4. Bochs runs 386 code silently** (W1), and NASM's `cpu 286` does not
  stop all of it (E4). A slip runs in every test and fails only on the AT.
  The check of M1 and the runs of M9 close this.
- **X5. `mformat -C` copies uninitialised memory of the mtools process into
  the image** (E5). The build never uses `-C`.
- **X6. A kernel stack overflow on the 286 is a triple fault, and so a
  silent reset,** unless the double fault is handled by a task with its own
  stack (D13).
- **X7. The 8254's channel 1 refreshes the AT's DRAM.** A kernel that
  reprograms "the timer" carelessly stops memory refresh, and the machine
  loses its memory. Only channel 0 is ever touched.
- **X8. An LDT the kernel never loaded.** The kernel has no LDT, but if it
  never runs `LLDT` with a null selector, LDTR keeps whatever the CPU started
  with. In Bochs that is a 64 KB LDT at linear 0, and a ring-3 program can
  load descriptors from it (*E10*). The kernel loads LDTR with 0 at start
  (*The boot*).
- **X9. Masking the cascade.** IRQ2 has no device of its own, so masking it
  looks harmless. It cuts off IRQ8-15, IRQ13 among them, and the program's
  next 287 instruction then stalls on BUSY (*E10*). IRQ2 stays unmasked.

### Where this roadmap recommends otherwise than the draft

- **The IDT is prefilled, but shorter than 256 entries:** it runs from vector
  00h to 30h (D10). Every vector beyond its limit still ends in a handled
  fault: a general protection fault whose error code names the vector. That
  is less to write and less to read, with the same behaviour.
- **The user program is a separate binary inside the kernel's image** (A3,
  D5), rather than kernel source.
- **A third build flavour, test** (A7, D16).
- **The repo layout adds directories:**
  - `src/include` for the constants that the boot code, the kernel and the
    program share;
  - `tests`;
  - `tools`;
  - `build` (*The architecture*).

## What the 80286 asks of the design

These facts shape everything that follows. They are from Intel's *80286 and
80287 Programmer's Reference Manual* and IBM's *Technical Reference*; E6
checked the ones that Bochs can show.

- **Protected mode is one way.** `LMSW` with PE set enters it, and nothing
  clears PE. The only way back to real mode is a reset. IBM's documented way
  is the 8042's command FEh, which pulses the CPU's reset line; its BIOS
  calls this "shutdown". After a reset the BIOS reads CMOS byte 0Fh to decide
  whether to run its full start-up: 0 means a soft reset. So the kernel never
  uses the BIOS, because it cannot. Reboot is a reset with CMOS 0Fh set to 0.
- **The instruction after `LMSW` must be a jump.** It flushes the prefetch
  queue; Intel asks for an intra-segment jump (10.4.2). rx286's jump is far,
  as IBM's BIOS does, and it also loads CS with a selector.
- **Addresses are 24 bits** (16 MB), and segments are at most 64 KB with a
  byte-exact limit. A word at offset FFFFh does not wrap: it is a general
  protection fault, or a stack fault on the stack.
- **A descriptor is 8 bytes:**
  - a 16-bit limit;
  - a 24-bit base;
  - an access byte (present, DPL, code/data or system, type);
  - **a last word that the 286 reserves and that must be zero.**

  A 386 or later reads that word as limit 16-19, granularity, default size
  and base 24-31. All zero means a byte limit, 16-bit code and a base under
  16 MB, which is exactly the 286's meaning. So prefilled descriptors with a
  zero top word behave alike on the AT and in Bochs. In E6, `info gdt`
  decoded each as a 286 descriptor: the code segments "16-bit", the TSS
  "16-Bit TSS".
- **System descriptors:**

  | Type | Meaning |
  |---|---|
  | 1 | available 286 TSS |
  | 2 | LDT |
  | 3 | busy 286 TSS |
  | 4 | call gate |
  | 5 | task gate |
  | 6 | interrupt gate |
  | 7 | trap gate |

  An interrupt gate clears IF and a trap gate does not.
- **Privilege:**
  - **The levels:** CPL is in CS's low two bits, RPL in every selector, DPL
    in every descriptor.
  - **Data:** a data segment loads only if max(CPL, RPL) ≤ DPL.
  - **The stack:** a stack segment needs DPL = CPL = RPL.
  - **Code:** code of more privilege is reached only through a gate.
- **From ring 3 to ring 0 the CPU changes stacks.** On an interrupt from
  ring 3, it loads SS:SP from the current TSS (SS0, SP0) and pushes the old
  SS, SP, FLAGS, CS, IP and, for some exceptions, an error code. So **a TSS
  is needed even without task switching**, and `LTR` must load one. A 286
  TSS is 44 bytes.
- **I/O and interrupts belong to IOPL.** At CPL > IOPL, `IN`, `OUT`, `INS`,
  `OUTS`, `CLI`, `STI` and the `LOCK` prefix are general protection faults
  (3.11.2, 10.3). A 386 or later no longer checks `LOCK`: in Bochs a locked
  instruction at CPL 3 runs (*E10*). The 286 has no I/O
  permission bitmap. A 386 or later looks for one in a 32-bit TSS, and with
  a 286 TSS denies every port, which is the same result (E6: Bochs' log
  says so). `POPF` and `IRET` at CPL > 0 leave IOPL alone, and at
  CPL > IOPL leave IF alone. Both happen silently (E6).
- **Privileged at CPL 0:** `LGDT`, `LIDT`, `LLDT`, `LTR`, `LMSW`, `CLTS`,
  `HLT`, and the undocumented `LOADALL`.
- **Not privileged on the 286:** `SMSW`, `SGDT`, `SIDT`, `SLDT` and `STR`. A
  program can read where the tables are. That is harmless here, because the
  addresses are fixed and documented anyway.
- **The kernel's tools for checking a program's pointers:** `ARPL` (raise a
  selector's RPL to the caller's), `VERR` and `VERW` (would this selector be
  readable or writable at its RPL), `LSL` (its limit) and `LAR` (its access
  byte). E6's system call used `ARPL`, `VERR` and `LSL` and rejected both a
  pointer past the limit and a null selector.
- **The exceptions:**

  | Vector | Exception | Error code |
  |---|---|---|
  | 0 | divide error | no |
  | 1 | single step (TF), a trap | no |
  | 2 | NMI | no |
  | 3 | `INT 3` (software: the gate's DPL applies) | no |
  | 4 | `INTO` (software: the gate's DPL applies) | no |
  | 5 | `BOUND` range exceeded | no |
  | 6 | invalid opcode | no |
  | 7 | processor extension not available (`ESC` with EM or TS set; `WAIT` with TS and MP) | no |
  | 8 | double fault | yes (0) |
  | 9 | processor extension segment overrun | no |
  | 10 | invalid TSS | yes |
  | 11 | segment not present | yes |
  | 12 | stack fault | yes |
  | 13 | general protection | yes |
  | 14, 15 | reserved | |
  | 16 | processor extension error: never on the AT (below) | no |
  | 17-31 | reserved | |

  - **A fault while delivering a double fault** puts the CPU in shutdown.
    Only NMI or RESET ends it (Intel, 9.6.2). AT-compatible boards turn a
    shutdown into a reset, and Bochs does (`reset_on_triple_fault=1`).
    IBM's *Technical Reference* does not say what the 5170 itself does, so
    M9 records it if MAME shows it.
  - **Gate DPL:** a software interrupt (`INT n`, `INT 3`, `INTO`) through a
    gate whose DPL is below CPL is a general protection fault, with error
    code n×8+2. The CPU's own exceptions ignore the gate's DPL.
  - **Beyond the IDT's limit:** an interrupt there is a general protection
    fault, with the same error code.
- **LDTR must be loaded.** Intel's start-up sequence loads it with a null
  selector if no LDT is needed (10.4.2). Bochs starts with a live LDT: base
  0, limit FFFFh, the real-mode vector table read as descriptors. In *E10* a
  ring-3 program loaded one of those descriptors into DS. The kernel runs
  `LLDT` with 0 (X8).
- **#TS is meant for a task gate.** Intel: "Exception 10 must be handled
  through a task gate to insure a proper TSS to process it" (9.6.4). The
  reason is a fault halfway through a task switch. Why rx286 does
  otherwise is under *The IDT*.
- **A program can set TF.** `POPF` in ring 3 may set the trap flag, which
  raises vector 1 after every instruction. The kernel treats that as a fault
  of the program (*The security model*).
- **The 287 on the AT:**
  - **Its errors:** its error signal "generates a hardware interrupt
    (interrupt 13)", which is IRQ13 on the slave 8259A, and holds BUSY
    latched until port F0h is written (IBM). So the 286's vector 16 is not
    used on the AT.
  - **The cost of missing IRQ13:** the 286 tests BUSY before most `ESC`
    instructions. An IRQ13 that never reaches the kernel therefore stalls
    the program's next 287 instruction. So IRQ2, the cascade that IRQ13
    comes through, is never masked (*E10*).
  - **The MSW:** MP set and EM clear let `ESC` and `WAIT` run.
  - **`FSETPM`:** must run once after the 286 enters protected mode, so the
    287 handles protected-mode operand addresses. It does nothing on Bochs'
    FPU.
  - **On Bochs** the error arrives at the next waiting FPU instruction (E8).
  - **On a 287** it arrives when the faulting instruction ends.
- **`LOADALL` (0Fh 05h)** is undocumented: neither reference mentions it.
  At CPL 3 a 286 is believed to raise a general protection fault, and M9
  records what a 286 core does. On Bochs' CPU the same bytes are `SYSCALL`,
  an invalid opcode (E6). Either way the kernel handles it; the attack suite
  expects the vector per emulator.
- **A20** is gated by bit 1 of the 8042's output port. Bochs' BIOS leaves it
  on (*E10*). No descriptor of rx286's reaches 1 MB, so its state cannot
  matter (D6).
- **The `POPF` erratum:** on some early 80286 steppings, `POPF` can let a
  pending interrupt in even though IF is 0 before and after. The kernel
  never uses `POPF` to keep interrupts off: it uses `CLI`, and `IRET` to
  return.

### E1. Bochs without a window

A 512-byte boot sector printed through port E9 and COM1, then wrote
"Shutdown" to port 8900h. The bochsrc used `display_library: rfb,
options="timeout=0"`.
- **Bochs stops at once in its debugger** and waits on standard input
  (`<bochs:1>`): the Debian build has the debugger compiled in. With
  `-rc cont.rc` holding `c`, it runs.
- **From start to exit:** 0.27-0.31 s of wall time and 0.22 s of CPU. The
  log is 12.7 KB.
- **`rfb` listens on port 5900.** Two runs at once both finished; the second
  takes the next port.

### E2. What a test can talk through, and how it ends

- **Port E9** (`port_e9_hack: enabled=1`): bytes go to Bochs' standard
  output.
- **COM1 to a file** (`com1: enabled=1, mode=file, dev=com1.out`): the bytes
  are in the file.
- **COM1 as a socket** (`mode=socket-server, dev=localhost:15551`): a Python
  client sent "rx286 says hi." and a boot sector echoed it back.
  - **A lesson:** the last byte was lost, because the guest wrote the shutdown
    port before the UART had sent it. A test build waits for the
    transmitter to be empty (line status bit 6) first.
- **The shutdown port:** Bochs logs `>>PANIC<< Shutdown port: shutdown
  requested` and **exits with status 1.**
- **`magic_break: enabled=1`:** `xchg bx, bx` stops in the debugger. A
  script `c`, `r`, `sreg`, `quit` dumped the registers, and Bochs **exited
  with status 0.**
- **`timeout` killing Bochs** gives status 124.
- **Debugger output after a breakpoint is lost from standard output at
  `quit`.** `debugger_log: file` keeps all of it (E6).

So the exit status cannot tell a pass from a failure: the shutdown port
always gives 1. The runner decides from the transcript instead: a test
passes if COM1 shows its expected lines and the closing `TEST END` line.

### E4. What NASM gives the layout

- **`cpu 286` rejects** `mov eax`, `movzx`, `pushad`, `push fs`,
  `mov cr0, eax`, and the 386's `loadall` (it accepts `loadall286`).
- **`cpu 286` lets through:**
  - 32-bit addressing: `mov ax, [ebx]` became `67 8B 03`, and
    `[ecx*2]` and `a32 lodsb` passed too;
  - `mov ax, fs`, which became `8C E0`;
  - `o32 lodsw`, which only warns.

  **So the build needs its own check:** M1's `tools/check-286` reads the
  listings.
- **`section.X.start` is not a scalar.** `(KERNEL_PHYS +
  section.ktext.start) & 0xFFFF` fails with "`&` operator may only be
  applied to scalar values", and `>> 16` likewise. Descriptor bases can't be
  computed from where NASM put a section.
- **Fixed offsets work.** With `section ktext start=KTEXT_OFF vstart=0` and
  `KTEXT_OFF equ 0x0100`, every base is a constant. The GDT came out with
  bases 10100h, 10800h and 11800h, and each section's labels count from 0.
  That is the offset within its own segment.
- **Labels of one section used in another resolve to the segment offset,**
  where they are used plainly:
  - `dw stub1` in the IDT gave 0005h;
  - `jmp 0x08:pm_entry` worked;
  - `ktext_end - 1` gives a limit.
- **Sections that overlap are fatal:** "sections ktext and kdata overlap!",
  exit 1. Fixed offsets are therefore safe: growth past one's room stops the
  build.
- **`%rep` with `%assign`** writes 256 gates and 256 stubs.
- **`[map all file]`** writes each symbol's file offset ("Real") and segment
  offset ("Virtual"), and does not change the output's bytes.

### E5. How mtools builds the floppy

- **`mformat -i img -f 1200 -B boot.bin`** keeps the boot sector's code and
  jump, and writes the BPB for a 1.2 MB disk:
  - 15 sectors a track, 2 heads, 224 root entries, 7 sectors a FAT;
  - media byte F9h, FAT12. But with `-R` (below), mformat writes F0h in the
    BPB and the FAT, and `-m 0xF9` puts F9h back;
  - the label, and 55AAh.

  `-f 1440` alike. **`-B` resets the reserved sectors to 1.**
- **`-R 4`** sets 4 reserved sectors. The option is missing from `mformat`'s
  usage line but is in its manual. The loader, written with `dd` into
  sectors 1-3, survives `mcopy`.
- **`mcopy` of a 40,000-byte `KERNEL.BIN`** to an empty disk took clusters 2-80
  in one run (`mshowfat`), and copied back identical.
- **Not reproducible as it stands.** Two builds differ in:
  1. **The last sector:** `mformat -C` (create the image) fills it with
     **uninitialised memory of the mtools process**. The bytes look like
     pointers, 00007FFC… and the like.
  2. **The serial number,** which is random.
  3. **The volume label's time stamp.**
  4. **The file's time stamps.**
- **Reproducible:**
  - make the image with `dd` from `/dev/zero` and run `mformat` without
    `-C`;
  - give `-N 52583836` (any fixed serial) and `-m 0xF9`;
  - export `SOURCE_DATE_EPOCH`.

  Two builds two seconds apart were identical, byte for byte.
- **`fsck.fat` is not installed** (`dosfstools`). `minfo`, `mdir` and
  `mshowfat` are.

### E6. The 286 design, end to end

A throwaway kernel of 9,728 bytes, and a boot sector that loaded it with INT
13h to 1000:0000:
- **Real-mode entry:** `LGDT` and `LIDT` of prefilled tables; both 8259As
  remapped to 20h-2Fh; `LMSW` with PE and MP; a far jump.
- **The tables:**
  - 8 GDT descriptors with a zero top word: kernel code, data and stack,
    the TSS, user code, data and stack;
  - 256 interrupt gates, all DPL 0 but 30h, which is DPL 3;
  - a 286 TSS holding SS0:SP0.
- **One common interrupt path** that sees the vector, the error code and the
  frame.
- **The ring-3 program** reads its test number through `INT 30h`, does one
  forbidden thing, and is restarted by the kernel at the next test.

### E7. Keys through the 8042

Inside E6, the kernel waited for the 8042's input buffer to be empty, wrote
command D2h to port 64h ("write keyboard output buffer"), then 1Eh to port
60h. **IRQ1 came, and port 60h read 1Eh,** the A key's make code in set 1.

Command D2h is from the PS/2's keyboard controller and later AT compatibles,
not from the 1984 AT's. So it is used only in test builds, to type a test's
keys through the real path: 8042, IRQ1, port 60h, the driver.

### E8. The 287's errors

Inside E6, the program unmasked zero-divide (`fldcw` 037Bh), divided 1 by 0
and ran `fwait`. **IRQ13 came on vector 2Dh** through the slave 8259A. The
handler wrote 0 to port F0h, ran `fnclex`, and sent EOI to the slave, then
the master.
- **`LMSW` left NE clear** on Bochs' CPU. NE is not a 286 bit; when it is
  clear, a 486 or later reports errors the AT's way, on IRQ13.
- **On Bochs the error comes at the next waiting instruction,** so the handler
  must not assume which instruction of the program it interrupted.

### E9. What can stand in for a real 286

Not run: installing needs `sudo`. From each project's documentation:
- **DOSBox-X 2024.03.01** (apt, 11 MB):
  - **Documented:** `cputype=286` and `286_prefetch` (protected mode, no
    V86); an option "segment limits" (on by default); an option "allow lmsw
    to exit protected mode" (default `auto`, which must be `false` here);
    `machine=ega`; `-set section property=value`; `BOOT` from a floppy image.
  - **Unknown:** whether the Debian build has its debugger, whether
    `cputype=286` rejects 386 opcodes, and how close its 8042, PIT and PIC
    are to the AT's.
- **MAME 0.264** (apt, 403 MB): the driver `ibm5170` is the IBM PC/AT, with
  an 80286 core, and `-debug` starts its debugger. It needs the 5170's BIOS
  ROMs, which IBM wrote and nobody may distribute. The owner would supply
  them.
- **86Box** (AppImage, not in apt): close emulation of real AT-class
  machines. It needs the 86Box ROM set. It has no debugger to speak of.
- **QEMU 8.2.2** (apt): no 286; its oldest CPU is a 486. Not needed (*Where
  we are*).

### E10. An independent check, re-running E6 with changes

A fresh reviewer checked the draft against the two references and the raw
outputs, and ran variants of E6 and new boot sectors in Bochs. What it found,
and what the roadmap now says:
- **Bochs starts with a live LDT.** E6's own debugger log shows `ldtr:0x0000,
  ... valid=1`: a base of 0 and a limit of FFFFh.
  - **In ring 3,** `LAR` accepted 59 selectors with TI = 1, and
    `mov ds, 000Fh` loaded. `info ldt` decodes the real-mode vector table as
    descriptors of DPL 3.
  - **Intel's start-up sequence** loads LDTR with 0 when no LDT is needed
    (10.4.2).
  - The kernel now does (X8, *The boot*).
- **Masking IRQ2 masks IRQ8-15.** With the master's mask at FCh, E6's 287 test
  timed out instead of reporting IRQ13 (X9, *The interrupt lines*).
- **`sti; cli` opens no window.** With a timer interrupt pending, `sti; cli`
  let no tick in, and `sti; nop; cli` let one in. `STI` takes effect after
  the next instruction (D15).
- **A program's `IRET` with NT set gives #TS(0) in Bochs,** and the log says
  "iret: TSS selector points to bad TSS". Intel's text in 10.1 says
  exception 13, and its `IRET` pseudocode (B-51) says #TS. The attack suite
  takes either, and M9 records the 286's (*The security model*).
- **A `LOCK` prefix at CPL 3 runs in Bochs.** Intel's 286 faults on it at
  CPL > IOPL (3.11.2). It is a known difference for M9.
- **The RTC raised IRQ8 once** with its periodic interrupt on and only EOI
  sent. It raised IRQ8 563 times in 10 ticks when the handler read register
  C. The flood test reads register C itself (*Testing*).
- **`megs: 1` gives 639 KB of base memory and no extended memory** (INT 12h
  returned 027Fh, INT 15h AH=88h returned 0). **A20 is on** after Bochs' BIOS:
  FFFF:0510 does not alias 0:0500.
- **386 prefixes can come second.** NASM puts segment, REP and LOCK prefixes
  first, so `mov ax, [es:ebx]` is `26 67 8B 03` under `cpu 286`, without a
  word. `check-286` looks at every prefix byte (*Testing*).
- **The original AT runs at 6 MHz** (IBM, 1-7), so the cost of a scroll was
  re-estimated (D14, D15).
- **Smaller corrections:** the media byte with `-R` (E5); the loader's 3
  sectors in the memory map; the accessed bits that the CPU sets in the GDT
  (*The GDT*); the IDT's one task gate; a double fault inside the
  double-fault task; and citations.

## Constraints

From the draft, and what follows from them:
- **Minimal:**
  - **Hard-coded:** whatever can be fixed at assembly time is fixed. That
    covers the tables, the memory map, the vectors, the hardware's ports and
    IRQs, and the user program's place.
  - **Hardware:** a driver exists only where the first delivery needs it
    (D20).
  - **Not minimal:** the demonstration shell need not be minimal (the
    draft).
- **The BIOS:**
  - **In the boot sector and loader only.** The kernel never calls it, never
    reads its data area, and relies on nothing it set up. The one exception
    is the text mode, which the loader sets through INT 10h for the kernel
    (D14).
  - **It cannot be called anyway** once the kernel is in protected mode.
- **No detection.** The machine is the one in *The machine*. The bochsrc
  describes the same machine, and a check keeps them in step (M10).
- **Safe:**
  - every vector and IRQ line has a handler;
  - no ring-3 program can make the kernel fault, hang, reset or leak;
  - a kernel bug is reported, never a silent reset (*The security model*).
- **Only 286 instructions,** checked on the binaries, and run on a real 286
  core (M1, M9).
- **One source for three builds:** release, debug and test, chosen by NASM
  macros (D16).
- **Top-notch code:**
  - one module per file, with a header saying what it does and what it
    exports;
  - every routine documented with its inputs, outputs, the registers it
    destroys and the flags it sets;
  - every port, selector, vector and address a named constant;
  - every table explained;
  - documents under `docs/` for the architecture, the memory map, the boot,
    the hardware, the interrupts, the system calls, the security model, the
    build, the tests and debugging (*The architecture*, M10).
- **Reproducible:** the same sources give the same image, byte for byte (E5).

### The boot

1. **The BIOS** loads sector 0 of drive A (the boot sector) to 0000:7C00h and
   jumps there with the drive number in `DL`.
2. **The boot sector:**
   - sets up a stack below 7C00h;
   - reads the reserved sectors 1-3 (the loader, D3) to 0000:7E00h with INT
     13h, retrying three times with a reset between;
   - jumps to it with `DL` unchanged.

   On failure it prints a message through INT 10h and waits for a key, then
   INT 19h.
3. **The loader:**
   - reads the FAT and the root directory into its buffers, using the BPB's
     geometry, and finds `KERNEL  BIN`;
   - follows its cluster chain and reads it **one sector at a time** to
     1000:0000h (X3). It checks the size against the room that `layout.inc`
     gives;
   - then, with the BIOS's help:
     - sets text mode 3 (INT 10h AX=0003h, 80x25 colour);
     - switches off the floppy motor (`out 3F2h, 0Ch`, X2);
     - disables interrupts and NMI (port 70h bit 7);
     - jumps to 1000:0000h.

   It hands the kernel nothing: no registers, no tables.
4. **The kernel's real-mode entry** (D4):
   - `LGDT` and `LIDT` from pseudo-descriptors that are constants;
   - programs both 8259As (ICW1-4, vectors 20h and 28h, cascade on IRQ2) and
     masks every line;
   - `LMSW` with PE and MP;
   - a far jump to the kernel's code selector.
5. **In protected mode the kernel:**
   - loads its data and stack selectors, `LTR` the TSS, and `LLDT` a null
     selector, since Bochs starts with a live LDT (X8);
   - zeroes its uninitialised areas;
   - runs `FNINIT` and `FSETPM`;
   - programs the PIT's channel 0 and the 8042's command byte, and parks the
     cursor;
   - unmasks the lines (D12) and enables NMI;
   - initialises COM1 in debug and test builds;
   - prints its banner, enables interrupts, and enters the program at ring
     3 through `IRET`.

The two sides of the jump at step 3 share only `layout.inc`: the address
1000:0000h and the image's maximum size.

### The image, and the physical memory map (D6, D7)

`KERNEL.BIN` is one flat binary. Each segment starts at a fixed offset of it,
so every descriptor's base is a constant (E4). The loader puts it at 10000h,
which is aligned to 64 KB. A segment's limit is its contents' exact size
where the kernel assembles them itself, and its full room where it does not.

| Segment | Physical | Room | In the file | Descriptor |
|---|---|---|---|---|
| real-mode entry | 10000h | 256 B | yes | none (real mode) |
| kernel code | 10100h | 8 KB | yes | `KCODE`, limit = size |
| kernel data: GDT, IDT, TSSs, variables, messages | 12100h | 4 KB | yes | `KDATA`, limit = size |
| program code (the shell, `incbin`) | 13100h | 8 KB | yes | `UCODE`, limit = room |
| program data (`incbin`) | 15100h | 4 KB | yes | `UDATA`, limit = room |
| kernel stack | 16100h | 1 KB | no: zeroed at start | `KSTACK` |
| double-fault stack | 16500h | 512 B | no: zeroed at start | `DFSTACK` |
| program stack | 16700h | 2 KB | no: zeroed at start | `USTACK` |
| (end) | 16F00h | | | |
| colour text, page 0 | B8000h | 4,000 B | | `VIDEO` |

The rooms are a first guess from E6 and the milestones' estimates. M4 and M7
confirm them, and `make sizes` reports how full each one is. NASM refuses a
segment that outgrows its room (E4), so a wrong guess stops the build; it
cannot corrupt the next segment.

The program's data segment includes its zeroed variables. The program is
assembled with the same `layout.inc`, so it knows its own rooms. It also
knows that each of its segments starts at offset 0. It knows nothing of the
kernel's.

### The GDT

| Selector | Name | Base | Limit | Access | What |
|---|---|---|---|---|---|
| 00h | null | | | | |
| 08h | `KCODE` | 10100h | size | 9Bh: present, DPL 0, code, readable, accessed | the kernel |
| 10h | `KDATA` | 12100h | size | 93h: present, DPL 0, data, writable, accessed | its tables and variables |
| 18h | `KSTACK` | 16100h | 3FFh | 93h | its stack (SS0 in the TSS) |
| 20h | `TSS` | in `KDATA` | 2Bh | 81h: 286 TSS, available | the one task; back link 0 |
| 28h | `DFTSS` | in `KDATA` | 2Bh | 81h | the double-fault task (D13) |
| 30h | `DFSTACK` | 16500h | 1FFh | 93h | its stack |
| 38h | `VIDEO` | B8000h | F9Fh | 93h | text page 0 |
| 40h (43h) | `UCODE` | 13100h | 1FFFh | FBh: present, DPL 3, code, readable, accessed | the program |
| 48h (4Bh) | `UDATA` | 15100h | 0FFFh | F3h: present, DPL 3, data, writable, accessed | its data |
| 50h (53h) | `USTACK` | 16700h | 7FFh | F3h | its stack |

- **The top word** of every descriptor is zero.
- **The accessed bit** is preset in every segment descriptor. The CPU then
  never writes the GDT, except for the TSS's busy bit, so M8's checksums can
  cover the whole GDT (*E10*).
- **There is no LDT** (D8), and LDTR holds a null selector.
- **The limit** is 57h, so selectors from 58h up are outside it. Loading one
  is a general protection fault, which the attack suite tries. Test builds
  with the fuzzer add `UFUZZ` at 58h, and their limit is 5Fh (*Testing*).

### The IDT (D10)

| Vectors | Gate | DPL | Handler |
|---|---|---|---|
| 00h-07h, 09h-1Fh | interrupt | 0 | the exception path: a program's fault, or a kernel panic |
| 08h | task, to `DFTSS` | 0 | the double-fault task (D13) |
| 20h-2Fh | interrupt | 0 | IRQ0-15: a driver, or D12's rule |
| 30h | interrupt | 3 | the system call |

The limit is 187h: 49 gates of 8 bytes, minus 1. **Any vector above 30h,**
whether by `INT n` from the program or by anything else, is beyond the limit.
That is a general protection fault whose error code is n×8+2, so it is
reported like any other fault, naming the vector. External interrupts cannot
come above 2Fh, since both PICs are programmed below it. **A program's
`INT 3` or `INTO`** goes through a DPL-0 gate and is also a general
protection fault (E6). Only `INT 30h` reaches the kernel by the program's
choice.

Every gate but 08h's is an interrupt gate, so the kernel runs with IF clear.
The two exceptions are `read_key`'s wait and the point after each line
`write` writes (D15).

**#TS (0Ah) gets an interrupt gate,** although Intel advises a task gate for
it (9.6.4). Intel's reason is a fault halfway through a task switch, where
the current TSS may not be whole. rx286 has two task switches only:
- **The double fault's,** where a fault while switching is a shutdown anyway.
- **A program's `IRET` with NT set,** which faults on the null back link
  before anything is switched. *E10* saw #TS(0) with the kernel's state
  intact.

A task gate would cost a third TSS and stack, and protect nothing more.

### The system calls (D9)

`INT 30h` with the function in `AH`. The result is in `AX`, and an error sets
CF. The calls preserve every register they do not return.

| AH | Call | In | Out |
|---|---|---|---|
| 0 | `exit` | | does not return: the kernel restarts the program |
| 1 | `write` | DS:SI buffer, CX length (at most 4,096) | AX = bytes written; CF and AX = `E_FAULT` on a bad buffer |
| 2 | `read_key` | AL = 0 to wait, 1 to poll | AL = ASCII (0 for none), AH = scancode; CF clear |
| 3 | `ticks` | | DX:AX = ticks since start, at 50 Hz |
| 4 | `time` (D20 B) | | the RTC, in BCD: CH century, CL year, DH month, DL day, BH hours, BL minutes, AL seconds |
| other | | | CF, AX = `E_NOSYS` |

**How a buffer is checked:**
1. Take the caller's DS from the frame, and `ARPL` it against the caller's CS
   from the frame, so its RPL is at least 3.
2. `VERR` it: `write` reads the buffer, and a call that wrote a buffer would
   use `VERW`.
3. `LSL` its limit, and check that SI + CX - 1 neither wraps nor passes it
   (CX = 0 is allowed and writes nothing).
4. Load it into ES and copy.

The GDT never changes and there is no LDT, so the check cannot go stale,
even across `write`'s interrupt windows (D15). E6 showed it refusing a pointer past the limit and a
null selector. Any selector the program can name has DPL 3 or is refused, so
the kernel never reads through a selector the program could not use itself.

### Faults, and what happens next (D11, D13)

- **The program faults:** a CPU exception with CPL 3 in the frame's CS, a
  287 error (IRQ13) while it ran, or the single-step trap. The kernel prints
  a fault report:
  - the vector's name, the error code, and CS:IP;
  - in debug builds, the registers too.

  It then restarts the program at its entry, with a fresh stack and `FNINIT`.
  The report goes to the screen and, in debug and test builds, to COM1.
- **Ctrl+Break:** the keyboard handler restarts the program the same way. If
  it interrupted a system call, a flag makes the call's return do it
  instead. A program that spins cannot hold the machine.
- **The kernel faults:** a CPU exception with CPL 0 in the frame, or an NMI.
  `panic` prints a panic screen (white on red):
  - the vector, the error code, CS:IP, the registers;
  - port 61h's status bits, for an NMI.

  It then masks NMI, disables interrupts and halts. A test build writes
  "PANIC" to COM1 and ends through the shutdown port.
- **A double fault** switches to `DFTSS` on its own stack (D13). The task
  reads the faulting state from `TSS` (the CPU saved it there), and panics.
  So **a kernel stack overflow is reported,** not turned into a silent reset
  (X6).
- **Ctrl+Alt+Del** writes 0 to CMOS byte 0Fh (a soft reset) and sends FEh to
  the 8042, which resets the CPU.

### The interrupt lines (D12)

- **At start:** every line is unmasked, IRQ2 too. Masking the cascade would
  cut off IRQ8-15, and with them the 287's errors (X9). IRQ2's own vector,
  22h, is never delivered.
- **A line with a driver** goes to its driver: 0 timer, 1 keyboard, 13 FPU.
- **A line without one, the first time:** the kernel prints "unhandled IRQ n",
  sends EOI, and masks the line. One message per line per boot, and a device
  that keeps interrupting can no longer flood.
- **IRQ7 and IRQ15** first read the PIC's in-service register (OCW3 0Bh). If
  the line's bit is clear, the interrupt was spurious:
  - no EOI to that PIC, except that a spurious IRQ15 still sends EOI to the
    master for the cascade;
  - a counter is incremented;
  - in debug builds, the kernel prints it.
- **NMI** panics (D13).

### The console

- **The screen:** text page 0 at B8000h through `VIDEO`, 80x25, light grey on
  black. The kernel's own messages are yellow, and the panic screen is white
  on red.
- **Scrolling** is a copy of 24 lines up, plus a blank last line.
- **The cursor** is set through CRTC registers 0Eh and 0Fh.
- **Control characters:** CR, LF, BS, TAB (to the next multiple of 8) and FF
  (clear). Other bytes below 20h are shown as their CP437 glyphs.
- **In debug and test builds** every character the console writes goes to
  COM1 as well. That copy is the transcript tests compare (*Testing*).

### The keyboard

- **The 8042's command byte** is written as 45h: translation to set 1 on (bit
  6), the system flag (bit 2), the output-buffer interrupt (bit 0). This
  follows IBM's definition in the *Technical Reference*. The keyboard itself
  is left as the BIOS reset it; its LEDs are *Later*.
- **IRQ1** reads port 60h:
  - it tracks Shift, Ctrl, Alt and Caps Lock;
  - it ignores the E0h and E1h prefixes of an enhanced keyboard, and the
    codes that follow;
  - it puts ASCII and scancode pairs in a ring of 16.

  When the ring is full, a key is dropped, and debug builds count the drops.
- **The layout** is US, as the AT's own keyboard.

### The 287 (D17)

The program may use it: MP is set and EM clear, so `ESC` and `WAIT` run.
- **The kernel never uses it.** With only one program, it saves no state.
- **At start, and at every restart,** the kernel runs `FNINIT`. `FSETPM` runs
  once, at start.
- **IRQ13:** the handler writes 0 to port F0h, runs `FNCLEX`, sends EOI to
  both PICs, and treats the error as a fault of the program.
- **Vectors 7 and 9** cannot come in normal use, but both are reported:
  - vector 7 needs EM or TS, and the kernel never sets either;
  - vector 9 means the 287's operand crossed a segment's end, which is a
    fault of the program.

## The security model

**The threat:** the ring-3 program is arbitrary code. The attack suite runs
the program as an attacker (M8). The shell is trusted no more than that.

**The promise:**
- **No program can make the kernel:**
  - fault, panic, reset or hang;
  - read or write memory outside the program's own three segments;
  - touch an I/O port;
  - disable interrupts;
  - keep the CPU from the kernel: the timer and keyboard interrupts always
    arrive.
- **Every way out is a reported fault,** after which the program starts
  again.

| Attack | What stops it | Expected |
|---|---|---|
| `CLI`, `STI`, `IN`, `OUT`, `INS`, `OUTS` | IOPL 0 | #GP(0) |
| A `LOCK` prefix | IOPL 0, on a 286 | #GP(0) on a 286; runs on Bochs (a known difference, *E10*) |
| `HLT`, `LGDT`, `LIDT`, `LLDT`, `LTR`, `LMSW`, `CLTS` | CPL 3 | #GP(0) |
| `LOADALL` (0Fh 05h) | CPL 3 on a 286; not an instruction on Bochs' CPU | #GP(0) on a 286, #UD on Bochs |
| `POPF` or `IRET` with IOPL 3 or IF 0 | the CPU ignores both at CPL 3 | silently ignored, then the next `CLI` faults |
| Setting NT and then `IRET` | `TSS`'s back link is 0 (Intel's advice, 10.1) | #TS(0) on Bochs (*E10*); Intel's text says #GP, its pseudocode #TS; M9 records the 286's |
| Loading a kernel selector into DS, ES or SS | DPL 0 | #GP(selector) |
| A selector past the GDT's limit, or an LDT selector (TI = 1) | the limit; LDTR loaded with a null selector (X8) | #GP(selector) |
| `CALL` or `JMP` far to kernel code, a TSS or a gate | DPL 0 | #GP(selector) |
| `INT n`: the IDT's DPL-0 gates (00h-2Fh), and beyond its limit (above 30h) | gate DPL; the IDT limit | #GP(n×8+2) |
| Writing through CS, or executing data | code is not writable; data is not executable | #GP(0), #GP(selector) |
| Past a segment's limit, a word at FFFFh | limits | #GP(0) or #SS(0) |
| `SP` run below 0, or past the stack's limit | `USTACK`'s limit | #SS(0), handled on `KSTACK` |
| Divide by zero, invalid opcodes, `BOUND` | | #DE, #UD, #BR |
| `TF` set by `POPF` | vector 1 is a fault of the program | single step reported, program restarted |
| 287 errors, unmasked | IRQ13 | reported as a fault |
| A 287 operand past a segment's end | | vector 9 or 13 |
| `SGDT`, `SIDT`, `SMSW`, `STR`, `SLDT`, `LAR`, `LSL`, `VERR` | unprivileged on the 286: they only read | allowed (the addresses are documented anyway) |
| A system call with a bad pointer: past the limit, a null selector, a kernel selector with RPL 3, CX that wraps | `ARPL`, `VERR`, `LSL`, bounds | `E_FAULT`; the program goes on |
| Unknown system calls, garbage registers | dispatch by AH | `E_NOSYS` |
| A spin loop, or blocking forever | the timer still runs; Ctrl+Break restarts | the machine stays responsive |
| Flooding `read_key` or `write` | a `write` is at most 4,096 bytes and opens interrupts after every line (D15) | no starvation: ticks and keys keep coming |
| Random bytes as code (the fuzzer, M8) | all of the above | every iteration ends in a fault or a restart; the kernel's tables and code unchanged |

**What is outside the promise:**
- **Hardware errors:** an NMI is a panic.
- **A double fault inside the double-fault task:** its TSS is busy, so the CPU
  cannot switch to it again, and shuts down. Intel's manual says only NMI or
  RESET ends a shutdown, and an AT-compatible board resets. Other faults
  inside the task go through the IDT to the panic path, on the task's own
  stack.
- **The kernel's own bugs:** they are reported, but they are bugs.
- **Physical access:** Ctrl+Alt+Del is the user's.

## Testing

Everything has a test (A5): every module, every system call, every vector,
every IRQ line, and every attack of *The security model*. `make test` runs
them all, and `make check` adds the checks on binaries, images and documents.
Seven layers, cheapest first:

### 1. At assembly time

- **Every file starts with `cpu 286`.** NASM runs with `-w+all -w+error`, so
  every warning fails the build, `o32` among them (E4).
- **`%error` guards:**
  - the boot sector is 510 bytes before 55AAh;
  - the loader fits the reserved sectors;
  - the program's code and data fit their rooms;
  - the GDT and IDT have the sizes their limits say.
- **NASM itself refuses overlapping segments** (E4).

### 2. On the binaries and the image (`make check`)

- **`tools/check-286`** reads NASM's listings, not the binaries, so data is
  never taken for code. It fails on:
  - a 66h, 67h, 64h or 65h byte anywhere among an instruction's prefixes. NASM
    puts segment, REP and LOCK prefixes first: `mov ax, [es:ebx]` is
    `26 67 8B 03` (*E10*);
  - `8Ch` or `8Eh` naming FS or GS;
  - a 0Fh opcode outside the 286's set (00h, 01h, 02h, 03h, 05h, 06h);
  - the 386's `loadall`.

  It fills the gap in `cpu 286` that E4 found. Its own test is E4's file of
  slips, every one of which it must flag.
- **`tools/check-image`:**
  - the BPB's fields for a 1.2 MB disk, with media byte F9h in the BPB and
    the FAT, and 55AAh;
  - 4 reserved sectors, with the loader's bytes in sectors 1-3;
  - `KERNEL.BIN` present, the right size, and in one run of clusters
    (`mshowfat`);
  - `fsck.fat -n` clean (`dosfstools`).
- **Reproducibility:** build the image twice into two directories, and `cmp`
  them.
- **`tools/lint`:**
  - a header on every file;
  - a header on every routine (inputs, outputs, destroyed registers, flags);
  - no number in an `in`, `out` or segment load that is not a named
    constant;
  - line length, and tabs.
- **The documents' checks:**
  - every constant of `ports.inc`, `selectors.inc` and `vectors.inc` appears
    in `docs/`;
  - the bochsrc templates agree with `ports.inc` and `layout.inc`;
  - every system call of `syscalls.inc` is in `docs/syscalls.md`.

### 3. Pure routines on the host (D18)

These routines take registers and memory and touch no hardware:
- scancode to ASCII under every shift state;
- decimal and hex printing of every 16-bit value;
- the shell's command parser and its number parsing;
- the loader's FAT12 entry decoding (odd and even entries, end of chain, bad
  clusters).

Each module that holds one also assembles alone into a test blob with a
table of entry points. pytest runs the blobs in Unicorn's 16-bit mode, with
thousands of cases a second and exact assertions. Unicorn is not a 286, so
only pure code is tested this way; everything else runs in Bochs.

### 4. Boot tests in Bochs

`tools/run-test` takes a test build's image and runs it:
- **The configuration:** `bochs/test.bochsrc`, with no window (`rfb`,
  `timeout=0`), the clock fixed, COM1 to a file, a debugger script of `c`,
  and a wall-clock limit of 20 s.
- **Typing:** the test build's `test.asm` types the test's keys through 8042
  command D2h (E7). The keys come from a `.keys` file, assembled into the
  image as make and break codes. It types one key per timer tick, but only
  while the program waits in `read_key` with its ring empty.
- **Ending:** when the keys run out and the program waits again, the kernel
  prints `TEST END` on COM1. It waits for the UART to empty (E2), then writes
  the shutdown port.
- **The verdict:** the runner compares COM1's transcript with the test's
  `.expected` file, line by line, and ignores lines marked `TRACE`. A
  `PANIC`, a missing `TEST END`, a timeout, or a difference fails.

A boot costs 0.3-0.5 s (E1, E6). Tests run in parallel, one Bochs each. Their
COM1 files differ, and `rfb` moves to the next free port.

**Suites:**
- **`tests/boot`:**
  - the image boots;
  - the loader finds a `KERNEL.BIN` that is fragmented (mtools makes one by
    writing and deleting other files first);
  - a missing or oversized kernel gives the loader's message;
  - a 1.2 MB and a 360 KB drive B are present (D2).
- **`tests/kernel`:**
  - the banner;
  - **the tables:** a debugger script dumps `info gdt`, `info idt`, `sreg`
    (LDTR null among them) and the TSSs with `x /22h`, and the runner
    compares the dump with the expected one (M4);
  - timer ticks at 50 Hz, against Bochs' fixed clock;
  - **`write`'s interrupt window:** a write of 4,096 newlines loses no tick
    (D15);
  - typed keys under every modifier;
  - Ctrl+Break restarts;
  - Ctrl+Alt+Del resets (the runner sees the BIOS start again);
  - the unhandled-IRQ rule, by the test build's device probes:
    - a diskette controller reset, for IRQ6;
    - a fixed-disk command, for IRQ14;
    - the RTC's periodic interrupt switched on, for IRQ8.

    Each line is printed once and masked. For IRQ8 the probe then reads RTC
    register C again and again. That would re-arm a flood (*E10*): the test
    checks that no IRQ8 reaches the CPU and that keys still arrive.
- **`tests/syscalls`:** each call, with good and bad arguments.
- **`tests/shell`:** each command of the shell, with its expected transcript.
- **`tests/panic`:** test builds with `TEST_PANIC=`:
  - a kernel fault;
  - an `ASSERT`;
  - a kernel stack overflow (it must arrive in the double-fault task, not
    reset);
  - an NMI, through the Bochs debugger's NMI command if it has one, else
    left to M9.

### 5. The attack suite (M8)

**`tests/attack`:** test builds with `TEST_PROGRAM=attack`, a program that
runs one attack per restart, as E6's did.
- **The attacks:** every row of *The security model*.
- **Each attack's expectation:** its expected fault line, with the vector, the
  error code and the IP; the IP is checked against the program's map.
- **After every attack** the kernel's test build checks a checksum of
  `KCODE`, the GDT, the IDT and both TSSs (less the busy bits), and
  `KSTACK`'s depth at the return to ring 3. A difference is a panic.

### 6. The fuzzer (M8)

**`tests/fuzz`:** `TEST_PROGRAM=fuzz` runs random code in ring 3.
- **The code segment:** the test build adds `UFUZZ`, a DPL-3 code descriptor
  over the program's data. This is the only place an executable alias of
  writable memory exists, and it is only in test builds.
- **Each iteration:**
  - fill 256 bytes with a seeded generator;
  - set random registers, including random segment registers among the
    program's selectors, null and kernel ones;
  - jump into the bytes.
- **The kernel:**
  - restarts the program on every fault, and on a watchdog of 50 ticks;
  - checks its checksums;
  - counts.
- **A run passes** when N iterations (10,000 by default) end without a panic,
  a reset, a hang or a checksum change. A failing seed is printed, and it
  becomes a regression test.

### 7. On a real 286 core (M9)

The boot, kernel, syscalls, shell and attack suites run again on the 286
emulator of D1. **The differences that are known** are listed in
`docs/emulators.md`, and the run checks them. Three are expected:
- **`LOADALL`** at CPL 3 is #GP on a 286 and #UD on Bochs;
- **a `LOCK` prefix** at CPL 3 is #GP on a 286 and runs on Bochs;
- **`IRET` with NT set** may differ between #TS and #GP (*E10*). **Any other difference is a failure:** usually
386 code that `check-286` missed, which then gets a rule in `check-286`.

## Debugging

- **`make debugger`** starts Bochs on the debug image with a window, the
  symbols loaded and a breakpoint at the kernel's entry. It uses
  `bochs/debug.bochsrc` with `debugger_log`, `magic_break` and
  `port_e9_hack`.
- **Symbols:** `tools/map2sym` turns NASM's map files into one Bochs symbol
  file. Each symbol is at its linear address: the segment's base from
  `layout.inc` plus its offset. `ldsym global "build/debug/rx286.sym"` then
  works in every segment, whatever its base (E6).
- **Breakpoints by name:** `lb "syscall"`. **Magic breakpoints:** the `BREAK`
  macro of `build.inc` assembles to `xchg bx, bx` in debug builds and to
  nothing in release builds.
- **The tables:**
  - `info gdt`, `info idt` and `sreg` decode 286 descriptors and gates;
  - `info tss` does not decode a 286 TSS, so use `x /22h` at the TSS's base,
    which `layout.inc` gives and `docs/debugging.md` lists (E6).
- **The logs:**
  - COM1 (`build/debug/com1.log`) has every `TRACE` line and the screen's
    copy;
  - Bochs' own log explains every exception it raises in plain words (E6);
  - its error lines (`e[CPU0]`) are the first thing to read when something
    faults.
- **Listings:** every assembly writes a listing (`-l`) and a map (`[map all]`)
  next to its binary. `ndisasm` reads any binary back.
- **Recipes in `docs/debugging.md`:**
  - a triple fault (Bochs resets: read the log's last exceptions);
  - a fault in the loader (real mode: break at 7E00h);
  - the wrong vector (check the PIC programming);
  - a fault that only a 286 shows (run M9's emulator with its debugger).
- **Scripted sessions:** a debugger script (`-rc`) with `debugger_log` captures
  everything. Standard output loses what follows a breakpoint (E2).

### D1. The emulators

**Decided: A** (2026-11-04), as recommended.

The draft leaves the emulator to this roadmap ("if that is the emulator you
decide one"). Bochs is installed, scriptable, AT-like and debuggable (E1-E8),
but it is not a 286 (W1).

- **A. Bochs for everything daily, DOSBox-X for the 286, and MAME too if the
  owner has the 5170's ROMs.** **Recommended.**
  - **For it:**
    - **Bochs** runs `make run`, `make debugger` and every suite, in half a
      second a boot.
    - **DOSBox-X** needs no ROMs and documents a 286 CPU type (E9).
    - **MAME's `ibm5170`** is the AT itself, with IBM's BIOS and a real 286
      core. It is the best proof available, if the ROMs are.
  - **Against it:**
    - **DOSBox-X is unproven:** whether it rejects 386 opcodes at
      `cputype=286` is unknown, and its PC is built for DOS games, not for
      the AT's details.
    - **M9 may find** that it cannot run the suites unattended.
- **B. Bochs only.** The least to install. But nothing would catch the 386 code
  that `check-286` misses, nor show the 286's own behaviour (`LOADALL`, the
  287's timing of errors).
- **C. MAME only, for the 286.** The most faithful, but it waits on ROMs that
  only the owner can supply.
- **D. 86Box.** Faithful, but an AppImage with a ROM set, and no debugger. It
  adds nothing over MAME.

### D2. The floppy drives

**Decided: A** (2026-11-04), as recommended.

The draft asks for two drives. It names no format.

- **A. Drive A 1.2 MB 5.25" (it boots); drive B 360 KB 5.25".** **Recommended.**
  These are the IBM AT's own drives, and the AT's BIOS knows both. Bochs
  emulates both (E3 booted a 1.2 MB image). mtools makes both (`-f 1200`,
  `-f 360`).
- **B. 1.44 MB 3.5" for both.** The format most people have. But it is not
  an AT drive, since the IBM AT's BIOS never supported it.

The image builds the same way either way, and only the BPB differs. The kernel
drives neither (D20).

### D3. Where the loader lives

**Decided: A** (2026-11-04), as recommended.

- **A. In the FAT's reserved sectors 1-3** (`mformat -R 4`, E5). The boot
  sector reads three fixed sectors. **Recommended.**
  - **For it:** the boot sector stays simple: no directory search in 446
    bytes of code. The loader has 1.5 KB, enough to search the root and
    follow `KERNEL.BIN`'s chain properly. The file system stays valid: the
    sectors are reserved by the BPB. The kernel is still loaded as a FAT
    file, as the draft asks.
  - **Against it:** the loader is not a file you can see with `mdir`, and
    updating it needs `dd`, not `mcopy`.
- **B. As a file, `LOADER.SYS`, found by the boot sector in the root
  directory.** The classic DOS layout. The search must fit beside the BPB in
  one sector. It works if the file is contiguous, and following a chain in
  the boot sector does not fit.

### D4. Who enters protected mode

**Decided: A** (2026-11-04), as recommended.

- **A. The kernel's real-mode entry** (`entry.asm`, E6). The loader only loads
  a file and jumps to it. **Recommended.**
  - **For it:** the loader knows nothing of the kernel: no GDT, no
    selectors. The kernel's tables and the code that loads them sit together.
    The entry uses no BIOS.
  - **Against it:** 30 lines of real-mode code in the kernel.
- **B. The loader** loads the tables from the kernel's image and enters
  protected mode itself. The kernel would be pure protected mode, but the
  loader would have to know the kernel's layout and the way into it.

### D5. How the image is assembled

**Decided: A** (2026-11-04), as recommended.

- **A. Flat binaries (`nasm -f bin`), each segment at a fixed offset from
  `layout.inc`. The program is assembled on its own and included with
  `incbin`.** **Recommended.**
  - **For it:**
    - **The bases are constants:** every descriptor base is one, which E4
      showed is the only way NASM allows.
    - **No linker.**
    - **Overflow stops the build:** a segment that outgrows its room is a
      fatal error.
    - **The program sees only `syscalls.inc` and `layout.inc`,** so even its
      source cannot reach a kernel symbol (A3).
  - **Against it:** the rooms are fixed by hand. The kernel's descriptors use
    the program's rooms, not its sizes, so its limits are looser than they
    could be. That is harmless, because the program can only reach its own
    segments' spare room.
- **B. One assembly, with the program's source `%include`d into the kernel.**
  This gives exact limits for the program as well. But nothing stops the
  program's source from naming a kernel label.
- **C. Objects and a linker** (`nasm -f obj` with OpenWatcom's `wlink`, or ELF
  and GNU `ld` with 16-bit relocations). It computes the layout. But it is
  another tool, a linker script for segments whose bases must still be
  constants, and more to explain, for an image of a few KB.

### D6. Memory, and A20

**Decided: A** (2026-11-04), as recommended.

- **A. rx286 uses the 640 KB of base memory and nothing above it, and leaves
  A20 as the BIOS left it. The bochsrc gives `megs: 1`: 639 KB base and no
  extended memory (*E10*).** **Recommended.**
  - **A20:** no descriptor reaches 1 MB, so its state cannot matter. Bochs'
    BIOS leaves it on, and no 8042 output-port code is needed.
  - **Room:** everything rx286 needs fits under 64 KB above 10000h (D7).
  - **A real AT** with extended memory runs the same kernel.
- **B. Enable A20 through the 8042 (command D1h, bit 1) and use extended
  memory.** It is needed only when something needs more than 576 KB, which
  nothing in the first delivery does. It is in *Later*.

### D7. The image's layout

**Decided** (2026-11-04), as recommended.

The fixed offsets and rooms are in the table in *The architecture*. The
choices in it:
- **The base:** 10000h. It is aligned to 64 KB, so a 286 base and a
  real-mode segment (1000h) name the same place, and no INT 13h read crosses
  a 64 KB boundary inside one sector (X3).
- **The order:** code, then data, then the zeroed areas, with the stacks last.
- **The rooms:** about twice E6's measures, and twice the estimates of M4-M7.

**Recommended:** the table, with M4 and M7 resizing the rooms once real code
exists. Each change is one line of `layout.inc`.

### D8. The program's descriptors

**Decided: A** (2026-11-04), as recommended.

- **A. Three GDT entries of DPL 3; no LDT.** **Recommended.** One program,
  three segments: an LDT adds a descriptor, `LLDT` and a table, and protects
  nothing more.
- **B. An LDT for the program.** This is the 286's model for many tasks, and
  it is in *Later*, with more than one program.

### D9. The system calls

**Decided: A** (2026-11-04), as recommended.

- **A. `INT 30h` through a DPL-3 interrupt gate; the function in `AH`; four
  calls (`exit`, `write`, `read_key`, `ticks`); CF for errors.**
  **Recommended.**
  - **For it:**
    - **One path:** the same stub and frame as every interrupt (E6).
    - **IF is cleared on entry,** so a call is never interrupted except where
      it waits (D15).
    - **CF in the frame's FLAGS** is easy for the program to test.
  - **Against it:** registers carry the arguments, so a call has at most
    about five arguments, which suits these four.
- **B. A call gate** (`CALL FAR` to a gate selector, parameters copied from
  the program's stack). The 286's own mechanism, with arguments on the
  stack. But it is a second path into the kernel, and interrupts stay
  enabled in it.
- **The number of calls** is a choice of its own. Four serve D19's shell,
  and D20 B adds a fifth, `time`:
  - colours, a cursor position, or a clock read from the RTC would each add
    one;
  - the shell can do colours itself with the console's control characters if
    the owner wants them (*Later*).

### D10. The IDT's size

**Decided: B** (2026-11-04), as recommended.

- **A. All 256 vectors prefilled,** every one beyond 30h going to an
  "unexpected interrupt" handler. This is what the draft's "idt all
  prefilled" suggests. 2 KB of table and 207 more stubs.
- **B. Vectors 00h-30h, with the IDT's limit at 187h.** **Recommended.**
  - **Above 30h:** every vector there is beyond the limit. On the 286 that
    is a general protection fault with error code n×8+2 (Intel's manual;
    E6's DPL case gives the same code). It is reported as a fault naming the
    vector.
  - **Nothing external comes above 2Fh,** since both PICs are programmed
    below it.
  - **The result:** the same behaviour as A, in 392 bytes, with nothing left
    unhandled.

### D11. When the program faults

**Decided: A** (2026-11-04), as recommended.

- **A. Report the fault, and restart the program at its entry with a fresh
  stack. Ctrl+Break restarts it as well.** **Recommended.** The system stays
  usable, the shell's `crash` commands show it, and a spinning program
  cannot hold the machine (A6).
- **B. Report the fault and halt.** Simpler, but every crash command then
  ends the demonstration, and the attack suite would need a boot per attack.

### D12. Interrupt lines without a driver

**Decided: B** (2026-11-04), as recommended.

- **A. Unmask every line; report every interrupt of a line without a
  driver.** This is the draft's words taken literally. Few devices interrupt
  again without their driver's acknowledgement: the RTC raised IRQ8 once,
  until register C was read (*E10*). But one that does would flood the screen
  and hold the CPU.
- **B. Unmask every line; the first interrupt of a line without a driver is
  reported, acknowledged, and the line masked. IRQ7 and IRQ15 are checked
  for spurious delivery first.** **Recommended.** Nothing goes unreported,
  nothing can flood, and the M5 probes test it.
- **C. Mask every line without a driver.** Nothing is ever reported, which
  meets the draft only on paper.

### D13. When the kernel faults

**Decided: A** (2026-11-04), as recommended.

- **A. A panic screen, then halt with NMI masked. The double fault goes to a
  task of its own, with its own stack.** **Recommended.** Intel's manual says
  that "a task gate must be used for the double fault handler". Without one,
  a kernel stack overflow is a triple fault and the AT resets in silence
  (X6). The task costs a TSS (44 bytes), a stack (512 bytes) and two
  descriptors.
- **B. A panic screen, with the double fault as an ordinary interrupt
  gate.** Smaller, but it fails exactly when it is needed.
- **Also:** a test build ends a panic through the shutdown port, so the runner
  sees it at once.

### D14. What the kernel programs, and what it takes from the loader

**Decided: A** (2026-11-04), as recommended.

- **A. The loader, which may use the BIOS, sets the text mode (INT 10h,
  mode 3) and stops the floppy motor. The kernel programs every device it
  uses itself, and relies on no other state.** **Recommended.** The kernel
  programs:
  - both PICs;
  - PIT channel 0, at 50 Hz (divisor 23864);
  - the 8042's command byte (45h);
  - the NMI mask;
  - COM1, in debug and test builds;
  - the CRTC's cursor.

  It never touches PIT channel 1 (X7).
- **B. The kernel also sets the EGA's mode itself,** about 60 register
  writes. It would then rely on no BIOS state at all, at a cost the draft's
  minimalism argues against.
- **The timer's rate: 50 Hz is recommended.**
  - **For it:** ticks are a simple unit for `uptime` and the test runner
    (2 per hundredth).
  - **The scroll:** it leaves a margin for the longest time the kernel keeps
    IF clear, one line and one scroll of `write`, which is several ms on a
    6 MHz AT (D15).
  - **Against 100 Hz:** 10 ms would come close to that time, and a tick could
    be lost.
  - **Against the BIOS's 18.2 Hz:** fewer interrupts, but awkward arithmetic.
  - **Whichever rate is chosen** is set explicitly, never inherited.

### D15. Interrupts inside the kernel

**Decided: A** (2026-11-04), as recommended.

- **A. Interrupt gates only, so the kernel runs with IF clear. It sets IF
  only at two points where its state is whole: in `read_key`, while it
  waits for a key (`sti; hlt; cli`), and in `write`, after each line it
  writes (`sti; nop; cli`). `STI` takes effect only after the next
  instruction, so `sti; cli` would open nothing (*E10*). One kernel stack.**
  **Recommended.**
  - **At most one nesting:** an IRQ at one of those points. Nothing can
    interleave with a half-finished change, so the kernel needs no locks.
  - **Ctrl+Break during a call** sets a flag. The call's return to ring 3
    restarts the program instead.
  - **Why `write` must open interrupts:** without the opening, a write of
    4,096 newlines would scroll 4,096 times. Each scroll copies 3,840 bytes,
    so IF would be clear for seconds, and ticks and keys would be lost. With
    it, IF is clear for one line and one scroll at most.
  - **What a scroll costs:** 1,920 words copied within the EGA's memory. The
    original AT runs at 6 MHz, and "8-bit bus operations to 8-bit devices
    take 6 clock cycles" (IBM, 1-7). IBM's EGA is an 8-bit card, though
    neither reference says so. A word read and written is then four bus
    operations, 24 clocks, and the scroll is about 46,000 clocks, roughly
    8 ms before the EGA's own wait states.
  - **Against the tick:** that is within a 50 Hz timer's 20 ms (D14), and
    tight against 100 Hz.
  - **M5 measures it:** the `write` test of *Testing* checks that no tick is
    lost.
- **B. Trap gates for the system call,** so calls run with interrupts on.
  Faster to respond, but every structure an IRQ touches then needs a guard.
- **C. Interrupt gates, and IF clear for a whole call.** The simplest. It is
  sound only if every call is short, and `write`'s scrolling is not.

### D16. The builds

**Decided: A** (2026-11-04), as recommended.

- **A. Three flavours from one source by NASM's `-d`: release, debug and
  test** (the table in *The architecture*). **Recommended.** The draft asks for
  release and debug. The tests need hooks that neither should carry: typing
  keys through D2h, the probes, the shutdown port.
- **B. Release and debug only, with the hooks in debug.** One flavour fewer.
  But then debug is no longer what a developer runs by hand, since it would
  end itself through the shutdown port.

### D17. The 287

**Decided: A** (2026-11-04), as recommended.

- **A. The program may use it. The kernel saves no state (there is one
  program), runs `FNINIT` at every restart, and treats IRQ13 as a fault of
  the program.** **Recommended.** It is what the draft's "80287" invites, and
  the shell's `fpu` command shows it.
- **B. Forbid it: set EM, so every `ESC` is vector 7, a fault.** Simplest, but
  then the 287 is present and useless.

### D18. Tests of pure routines on the host

**Decided: A** (2026-11-04), as recommended.

- **A. Unicorn and pytest** (*Testing*, layer 3). **Recommended.** Thousands of
  cases a second for the scancode table, number formatting, the parser and
  FAT12 decoding, with exact assertions. It costs two packages.
- **B. Only in the emulator:** routines tested through boot tests. That needs
  no packages, but each case costs a boot, so tests cover a few cases where A
  covers all.

### D19. The shell's commands

**Decided** (2026-11-04), as recommended.

The draft asks for "a few different commands to demonstate the kernel works",
and the shell need not be minimal. **Recommended:**

| Command | Shows |
|---|---|
| `help` | the commands |
| `echo text` | `write`, and the shell's parser |
| `clear` | the console's FF |
| `uptime` | `ticks`, as h:mm:ss.cc |
| `date` | `time`, as yyyy-mm-dd hh:mm:ss (D20 B) |
| `keys` | each key's scancode and ASCII until Esc: the keyboard driver |
| `fpu` | √2 and π to 18 digits by the 287 |
| `mem` | the program's own segments: base, limit, from `layout.inc` |
| `crash gp`, `ud`, `de`, `ss`, `io`, `cli`, `hlt`, `int`, `kernel`, `call`, `write`, `fpu`, `tf`, `nt` | one attack each; the kernel's report, and the shell back |
| `spin` | a loop forever; Ctrl+Break gets the shell back |
| `exit` | the `exit` call; the shell starts again |

A line editor with backspace, a prompt, and a history of one line (Up
repeats the last) make it pleasant. A longer history is *Later*.

### D20. Drivers in the first delivery

**Decided: B** (2026-11-04), against the recommendation: the owner chose the RTC and a `date` command.

- **A. Timer, keyboard, console and the 287; COM1 output in debug and test
  builds. No driver for the diskettes, fixed disks, COM2-4, LPT1-2, the RTC
  or the speaker.** Their interrupts follow D12. **Recommended.** It is what
  the first delivery's program needs, and the kernel stays minimal. Each of
  the others is in *Later*.
- **B. Add the RTC for a `date` command:** about 60 lines and a fifth system
  call.
- **C. Add serial input,** so the shell can be driven over COM1 (E2's socket):
  about 80 lines, IRQ4, a second input to `read_key`. Tests do not need it,
  since D2h types through the real keyboard path (E7).

### D21. Reboot

**Decided: A** (2026-11-04), as recommended.

- **A. Ctrl+Alt+Del, in the kernel's keyboard driver: CMOS 0Fh = 0, then
  8042 command FEh. No system call to reboot.** **Recommended.** A program
  cannot reset the machine, which is a kind of crash, while the person at
  the keyboard can.
- **B. A `reboot` system call,** so the shell can offer `reboot`. It is
  convenient, but it is a way for any program to end the system.

## The milestones

Each milestone is one commit or a few, and each commit leaves `make check`
green. Sizes are in lines of assembly and tools, with comments: S is up to
300, M up to 800, L more. Each milestone updates the documents it touches,
and records itself in *Status*.

### M1. The repo, the Makefile, `make doctor`, the Bochs configurations, the test runner (M, about 700)

* **What:**
  - **The layout of *The architecture*:** `src/`, `docs/`, `tests/`, `tools/`,
    `bochs/`, `.gitignore` for `build/`.
  - **`src/include/`:** `layout.inc`, `ports.inc`, `selectors.inc`,
    `vectors.inc`, `syscalls.inc`, `descriptors.inc`, `build.inc`. Constants
    and macros only, each documented.
  - **The Makefile:** every target of *The architecture*, three flavours, a
    listing and a map next to every binary, and the image built by E5's
    recipe.
  - **`tools/doctor`,** as in *Tooling*.
  - **`tools/check-286`,** with E4's slips as its own test.
  - **`tools/map2sym`.**
  - **`tools/check-image`.**
  - **`tools/lint`.**
  - **`tools/run-test`,** the runner of layer 4.
  - **`bochs/`:** the templates `run`, `debug` and `test`, from E3's
    bochsrc with `mode=gui` for the speaker, drive B at 360 KB (D2), and the
    paths filled in by the Makefile.
  - **A placeholder boot sector** that prints `TEST END` on COM1 and ends, so
    the runner, the image and every check run end to end from the first
    commit. M2 replaces it.
  - **`docs/`:**
    - `hardware.md` (from *The machine*);
    - `building.md`, `testing.md`, `debugging.md` and `style.md`, the
      conventions every later file follows;
    - stubs for the rest.
  - **`README.md`.**
* **Why first:** every later milestone is built, checked and tested by it.
* **Done when:**
  - `make doctor` reports every required tool;
  - `make test` passes the placeholder's boot test in under 2 s;
  - `make check` passes `check-286` (and `check-286` fails on E4's slips);
  - two builds of the image are identical;
  - `make debugger` stops at 7C00h with symbols.
* **Decisions:** D1 (the templates), D2, D6 (`megs: 1`), D16, D18 (the
  runner's layer 3 scaffolding).

### M2. The boot sector (S, about 150)

* **What:**
  - **`src/boot-sector/boot-sector.asm`:**
    - a BPB that `mformat -B` fills in;
    - a stack;
    - reads sectors 1-3 to 7E00h with three tries and a disk reset between;
    - jumps to 0000:7E00h with `DL` kept.
  - **Errors:** a message through INT 10h, a key, INT 19h.
  - **In debug and test builds,** it writes one `TRACE` character to COM1
    through INT 14h, so the runner sees it ran.
* **Done when:**
  - an image with a stub loader (which prints and ends) boots in the runner;
  - an image whose reserved sectors are zeroed gives the boot sector's
    message;
  - `check-image` checks the BPB.
* **Decisions:** D3.

### M3. The boot loader (M, about 400)

* **What:**
  - **`src/boot-loader/`:**
    - read the FAT and the root directory with the BPB's geometry (CHS
      from the logical sector);
    - find `KERNEL  BIN`;
    - follow its chain one sector at a time to 1000:0000h;
    - refuse a kernel bigger than `layout.inc`'s room.
  - **The hand-over** (D14): text mode 3, the floppy motor off, interrupts and
    NMI off, a jump to 1000:0000h.
  - **FAT12 decoding** in a module of its own, tested on the host (D18).
  - **Messages,** for a missing kernel, a read error or a kernel too large.
* **Done when:** the `tests/boot` suite passes:
  - a fragmented kernel loads;
  - a missing or oversized kernel gives the right message;
  - a stub kernel that prints over COM1 runs.
* **Decisions:** D3, D4, D7, D14.

### M4. The kernel's entry, its tables, and the panic path (M, about 700)

* **What:**
  - **The modules** `entry`, `start`, `gdt`, `idt`, `tss`, `interrupt`,
    `panic` and `print`, and the console's first half (write a character,
    scroll, the panic colours).
  - **The tables:** all of *The architecture*'s, including `DFTSS` and its
    task gate.
  - **Vectors:** every one from 00h to 2Fh goes to the panic path for now,
    and 30h answers `E_NOSYS`.
  - **The start:** `LLDT` with a null selector (X8), the zeroed areas,
    `FNINIT` and `FSETPM`, the PICs with every line masked, the banner.
  - **`ASSERT`, `TRACE` and `BREAK`** from `build.inc`.
* **Done when:**
  - the tables test of `tests/kernel` passes: the debugger's dump of the GDT,
    the IDT, the TSSs and LDTR matches the expected one;
  - the `tests/panic` builds give their panic screens:
    - a divide in the kernel;
    - an `ASSERT`;
    - a stack overflow, which arrives in `DFTSS`;
  - `make sizes` shows the kernel's code and data within their rooms;
  - `check-286` is clean.
* **Decisions:** D4, D5, D6, D7, D10, D13.

### M5. The drivers, and a rule for every IRQ (M, about 800)

* **What:**
  - **`pic`:** EOI, masking, the spurious checks, D12's rule.
  - **`timer`:** 50 Hz and the 32-bit count.
  - **`keyboard`:** the command byte, set 1, the modifiers, the ring,
    Ctrl+Alt+Del, Ctrl+Break.
  - **`console`:** the cursor, TAB, FF, and the COM1 copy.
  - **`serial`:** COM1 output.
  - **`fpu`:** IRQ13.
  - **`rtc`:** register B set to 24-hour BCD; the date and time read (D20 B).
  - **NMI to `panic`.**
  - **`test.asm`:** typed keys through D2h, the device probes, and the end
    through the shutdown port.
  - **The host tests** of the scancode table (D18).
* **Done when:** `tests/kernel` passes:
  - ticks against Bochs' fixed clock;
  - `write`'s interrupt window loses no tick;
  - every key under every modifier;
  - IRQ6, IRQ14 and IRQ8 each reported once and masked. The machine still
    answers keys while the probe re-arms the RTC;
  - Ctrl+Alt+Del resets;
  - an IRQ13 raised by a kernel test reports.
* **Decisions:** D12, D14, D15, D17, D20 (B: the RTC), D21.

### M6. Ring 3 and the system calls (M, about 500)

* **What:**
  - **Into ring 3:** `IRET` to the program at its entry, through a frame
    built by the kernel, with FLAGS 0202h.
  - **`fault`:** the report, and the restart.
  - **`syscall`:** the five calls, the pointer check, CF and the errors.
  - **Ctrl+Break and IRQ13** restart the program, deferred while a call
    runs (D15).
  - **A first attack program:** E6's 19 cases, plus these cases of *The
    security model*: TF, NT with `IRET`, `LOCK`, LDT selectors, and
    selectors past the GDT.
* **Done when:**
  - `tests/syscalls` passes, with every call given good and bad arguments;
  - the first attack program's every case gives its expected line.
* **Decisions:** D8, D9, D11, D15.

### M7. The demonstration shell (L, about 900)

* **What:**
  - **`src/userland/`:** the shell of D19, with a prompt, a line editor and

  - **The commands:** `help`, `echo`, `clear`, `uptime`, `date`, `keys`,
    `fpu`, `mem`, `crash ...`, `spin` and `exit`.

### M8. The attack suite and the fuzzer (M, about 600)

* **What:**

* **Done when:**
  - every attack gives its expected line;

### M9. The suites on a real 286 core (S-M, about 300)

    - COM1 to a file;

* **Risks:** DOSBox-X may not reject 386 opcodes at `cputype=286`, or may not

### Later

Each needs a roadmap of its own when the time comes:
- **More programs:**
  - loading programs from disk;
  - an LDT and a TSS each (D8);
  - scheduling, with the 287's state saved per task (TS and vector 7).
- **Drivers:**
  - diskettes (DMA channel 2);
  - fixed disks (PIO, IRQ14);
  - a FAT12/FAT16 driver in the kernel;
  - serial input (D20 C);
  - parallel printers;
  - the speaker.
- **Extended memory** (D6 B).
- **The keyboard:** its LEDs, and the AT's typematic rate, both of which need
  commands to the keyboard with their acknowledgements.
- **The console:** colours, and a cursor position, as system calls or control
  sequences.
- **The shell:** a longer history.

### Why this order

- **The tools before any code (M1).** Each later step is then tested the day
  it is written.
- **Boot (M2, M3) before the kernel,** because the kernel is tested from a real
  boot.
- **The tables and the panic path (M4) before the drivers.** Every mistake in
  the drivers then lands in a handled fault with a report, not a reset.
- **The drivers (M5) before ring 3 (M6),** because ring 3 needs the timer and
  the keyboard to be told apart from faults.
- **The shell (M7)** comes after the calls it uses.
- **The attack suite (M8) after the shell,** so it covers the whole system
  as delivered.
- **The 286 core (M9)** comes once the suites exist. It could be run earlier,
  by hand, and it should be if DOSBox-X turns out not to run unattended.
- **The documents (M10) last only in their final form.** Every milestone
  writes its own part, and M10 completes and reviews them.

## Risks

| Risk | What it would do | What reduces it |
|---|---|---|
| 386 code that neither `check-286` nor Bochs notices | runs in every test, fails on an AT | M9 on a 286 core; each slip becomes a `check-286` rule |
| DOSBox-X is not 286-faithful, or cannot run unattended | M9 proves less | MAME with the owner's ROMs (D1); manual runs |
| Bochs differs from the AT in a way the kernel relies on (the 287's timing of errors, D2h, the PIT's start, a live LDT and A20 at start, `LOCK` at CPL 3) | a test passes that the AT would fail | the kernel relies on no such thing (E8's handler, `LLDT` 0), D2h is test builds only, M9 lists the known differences |
| An estimate of the AT's timing is wrong (a scroll on the EGA, D15) | ticks lost on a real AT | 50 Hz leaves a margin (D14); the `write` test; M9 |
| Bochs 2.8 or later changes the configuration syntax | the templates stop loading | `make doctor` pins 2.7.x; the templates are three short files |
| The rooms of D7 are too small | the build stops (by design) | M4 and M7 resize them; `make sizes` warns at 90% |
| The fuzzer finds a hole in the CPU's emulation, not in rx286 | a false alarm, or a real hole hidden | each failing seed is replayed on the 286 core (M9) before it is called a kernel bug |
| Test flakiness from wall-clock timing | tests fail at random | the clock fixed (`clock: sync=none, time0=`), typing paced by the kernel's own ticks, never by wall time |
| The draft's line 27 meant more than tests | a requirement missed | asked (*Left open for the owner*) |
